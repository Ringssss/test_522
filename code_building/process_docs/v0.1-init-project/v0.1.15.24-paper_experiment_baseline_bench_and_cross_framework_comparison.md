# v0.1.15.24 — 论文实验：Baseline Bench 脚本 + 跨框架 Benchmark 对比

## 主题

为论文实验搭建公平的 benchmark 对比框架：(1) 编写 baseline dInfer 的 throughput bench 脚本，(2) 编写 SGLang dLLM bench 脚本，(3) 在统一配置下（GSM8K, pad=128, gen=256, block=32, threshold=0.90）完成四种引擎的性能对比，(4) 修复 TV6 在 DP=1 下的兼容性问题。

## 动机

上轮 (v0.1.15.23) 完成了 TV6 patch 独立模块和动机图，但 benchmark 对比中的"Vanilla"不是真正的 baseline——我们的修改版 dInfer 包含了 QKVParallelLinear（原生 TP 分片）、DP=2 支持、flash_attn 替换、fused_rmsnorm、OPT-2（skip logits.float）、SP-LM Head 等优化，它们没有被显式标注。本轮目标是用完全未修改的 `baseline_dInfer`（`lib_cite/baseline_dInfer`）建立真正的 baseline，并与 SGLang 做跨框架对比。

## 实验 1: Baseline dInfer 模型文件差异分析

### 设计动机

确认 baseline_dInfer 和我们的修改版 dInfer 在模型层面的具体差异，评估 benchmark 公平性。

### 方法

用 `diff` 对比两个 `modeling_llada2_moe.py`（baseline 2003 行 vs 修改版 4782 行，差异 2923 行），逐模块分析。

### Attention 层差异

**Baseline**：
```python
# __init__ 中
self.tp_size = 1  # 硬编码
self.query_key_value = nn.Linear(hidden_size, (num_heads + 2*kv_heads) * head_dim, ...)
self.dense = nn.Linear(num_heads * head_dim, hidden_size, ...)
```
构建时用 `nn.Linear` 全量权重。调用 `model.tensor_parallel(tp_size)` 后通过 regex 匹配 `_tp_plan` 动态替换为 `QKVParallelLinear`/`RowParallelLinear`，`weight_loader` 在内存中做 shard。

**修改版**：
```python
# __init__ 中
self.tp_size = get_tensor_model_parallel_world_size()  # 动态获取
self.num_heads = total_num_heads // self.tp_size  # 构建时就分
self.query_key_value = QKVParallelLinear(hidden_size, head_dim, total_num_heads, total_num_kv_heads, ...)
self.dense = RowParallelLinear(total_num_heads * head_dim, hidden_size, ...)
```
构建时直接用 vllm Parallel Linear，`load_weights` 按 shard 加载。

**TP>1 兼容性 bug**：baseline 的 `FlashAttention2.forward` 用 `self.num_heads`（全量）做 view，但 `QKVParallelLinear` 输出的是 local heads → shape mismatch。`SdpaAttention.forward` 有 `self.num_heads//self.tp_size` → 正确。因此 baseline 在 TP>1 下**只能用 sdpa**。

**KV heads 限制**：LLaDA2-mini `num_key_value_heads=4`。TP=8 时 `4//8=0` → crash。最大 TP=4。

### MoE 层差异

Baseline 直接调 `experts.forward_impl(hs, rl)`。修改版用 `_moe_forward_with_context()` 包装——这是 TV6 patch 的 hook 点。修改版还加了 EPLB 支持（`enable_eplb`, `num_redundant_experts`）和 SP 模式（`set_sequence_parallel()`, `forward_sp()`）。

### generate_uniform.py 差异

Baseline 的 while 循环：`while (block == mask_id).sum() > 0`——无跨 DP 同步，DP=2 下不同 rank 的循环次数可能不同 → AllToAll deadlock。修改版加了 DP 全局收敛检查（`all_reduce(MAX)` + `unroll_k=1`）。

### 结论

Baseline 受限于 TP=4（4 GPU），不支持 DP>1，Attention 只能用 sdpa，MoE 无 SP 模式。

## 实验 2: bench_baseline_dinfer.py 编写

### 设计动机

编写与 `bench_tv6_throughput.py` 结构对齐的 baseline benchmark 脚本，方便后续 A/B 插桩。

### 兼容性问题与解决

**问题 1: `is_torch_fx_available` ImportError**
```
ImportError: cannot import name 'is_torch_fx_available' from 'transformers.utils.import_utils'
```
transformers 5.3.0 已移除此函数。baseline `modeling_llada2_moe.py` line 51 直接 import。
**解决**：bench 脚本开头 runtime shim：
```python
import transformers.utils.import_utils as _tui
if not hasattr(_tui, 'is_torch_fx_available'):
    _tui.is_torch_fx_available = lambda: hasattr(torch, "fx")
```

**问题 2: `ROPE_INIT_FUNCTIONS['default']` KeyError**
baseline 代码依赖 transformers 旧版的 RoPE 初始化。
**解决**：bench 脚本开头注入 default RoPE init function。

**问题 3: TP=8 crash**
首次尝试 `torchrun --nproc_per_node=8`：
```
RuntimeError: shape '[1, 180, 3, 128]' is invalid for input of size 92160
```
`SdpaAttention.forward` line 1030: `num_heads//tp_size = 16//8 = 2`, `kv_heads//tp_size = 4//8 = 0` → 3 heads × 128 dim = 384 ≠ 92160/180 = 512。
**解决**：改为 `--nproc_per_node=4`（TP=4）。

**问题 4: batch=512 OOM**
```
torch.OutOfMemoryError: Tried to allocate 19.19 GiB
```
`logits.float()` 在 `modeling_llada2_moe.py` line 1921 将 `[512, seq_len, 157184]` bf16 → float32。我们的 OPT-2 (`DINF_SKIP_LOGITS_FLOAT=1`) 跳过了这步，baseline 没有。
**解决**：batch=512 记为 OOM，最大可用 batch=256。

### 脚本关键设计

- `sys.path.insert(0, baseline_dInfer/python)` 确保 import baseline dinfer
- `config._attn_implementation = "sdpa"` 显式设置
- `model.tensor_parallel(tp_size)` 后置 TP
- `--pad-to N`：截断/pad 所有 prompt 到固定 N tokens
- `--no-cache`：BlockDiffusionLLMAttnmask 模式
  - baseline 原版 `assert prompt.shape[0] == 1`，monkey-patch `batched_generate()` 支持 batch>1
  - 修复：`bd_attn_mask.repeat(batch_size, 1, 1)` + `pos_ids.repeat(batch_size, 1)` + `torch.all(decode_compl)`

## 实验 5: d1t4e4 消融——隔离 DP overhead

### 设计动机

确认小 batch 下的性能差距来自 DP=2 overhead 还是 TV6 本身。用 4 GPU TP=4 DP=1 跑我们的系统（Vanilla 和 TV6）。

### 新增 --tp-size 参数

`bench_tv6_throughput.py` 原逻辑 `tp_size = 4 if world_size == 8 else 2`，4 GPU 时会设 tp=2。新增 `--tp-size` 参数覆盖。

### TV6 DP=1 crash 排查过程

**第一次尝试**：
```
AttributeError: 'NoneType' object has no attribute 'local_sizes'
```
tv6_patch.py line 159: `ctx.dp_metadata.local_sizes = _tv6['compact_sizes']`。DP=1 时 `dp_metadata=None`。

根因追踪（`vllm/forward_context.py` line 352-354）：
```python
dp_metadata: Optional[DPMetadata] = None
if vllm_config.parallel_config.data_parallel_size > 1 and ...:
    dp_metadata = DPMetadata.make(...)
```
**只有 DP>1 才创建 dp_metadata。**

**第二次尝试**（加 dp_metadata guard）：
```
AssertionError: assert self.all2all_manager is not None
```
`cuda_communicator.py` line 312。

根因追踪（`base_device_communicator.py` line 119-122）：
```python
use_ep = config.parallel_config.data_parallel_size > 1
self.use_all2all = self.is_ep_communicator and use_ep
```
**只有 DP>1 才初始化 all2all_manager。**

**第三次尝试**（跳过 dispatch/combine）：
```
torch.AcceleratorError: CUDA error: invalid configuration argument
```
DP=1 跳过 dispatch 后，每个 rank 只有 N/4 SP tokens 直接进 fused_moe kernel。但 expert_map 指向的 experts 分布在所有 4 个 rank 上，kernel 访问了不存在的 expert → crash。

**理解转变**：Vanilla d1t4e4 能跑是因为走 AllReduce EP 模式——每个 rank 冗余持有全量 tokens，本地 64 experts 计算后 AllReduce。TV6/BSP-G 走 AgRs SP 模式——tokens 分片，必须 dispatch gather → 本地计算 → combine scatter。两种模式根本不同，不能简单跳过 dispatch。

### 正确修复（tv6_patch.py 三处改动）

**改动 1**：apply_tv6 开头手动初始化 EP group 的 all2all_manager
```python
if dp_size <= 1 and ep_group.device_communicator is not None:
    comm = ep_group.device_communicator
    if comm.all2all_manager is None:
        from vllm.distributed.device_communicators.all2all import AgRsAll2AllManager
        comm.all2all_manager = AgRsAll2AllManager(comm.cpu_group)
```
**原理**：vllm 认为 DP=1 不需要 EP dispatch（走 AllReduce），但 BSP-G 的 SP layout 需要。手动创建 AgRsAll2AllManager 让 EP group 具备 AllGatherV/ReduceScatterV 能力。

**改动 2**：tv6_forward_impl 中 DP=1 时创建临时 DPMetadata
```python
if ctx.dp_metadata is None:
    from vllm.forward_context import DPMetadata
    ctx.dp_metadata = DPMetadata(
        max_tokens_across_dp_cpu=torch.tensor([N_sp]),
        num_tokens_across_dp_cpu=torch.tensor([N_sp]),
    )
ctx.dp_metadata.local_sizes = _tv6['compact_sizes']
```
combine 后恢复 `ctx.dp_metadata = None`，确保后续 orig_fn fallback 路径看到 None（走 AllReduce 模式判断）。

**改动 3**：fallback 路径 `_run_full_moe()` 函数

当 `compute_mask_sp is None`（block 首步/M=5 刷新步）时 DP>1 用 orig_fn，DP=1 用新函数 `_run_full_moe()`。

**问题根因**：orig_fn（vllm FusedMoE.forward_impl）在 DP=1 下：
- `do_naive_dispatch_combine = (self.dp_size > 1)` = False → 跳过 dispatch/combine
- `is_sequence_parallel = True`（BSP-G 设的）→ 跳过 AllReduce
- 结果：每个 rank 只有本地 64 experts 对本地 N/4 tokens 的贡献（缺少其他 192 experts）

`_run_full_moe()` 手动做 dispatch → fused_moe kernel → combine：
```python
def _run_full_moe(self, hidden_states, router_logits):
    # 创建临时 dp_metadata
    ctx.dp_metadata.local_sizes = [N_sp] * ep_world  # 全量 sizes
    hs_g, rl_g = ep_group.dispatch(hidden_states, router_logits, self.is_sequence_parallel)
    # ... invoke_fused_moe_kernel 两次 (w13 + w2) ...
    y_sp = ep_group.combine(out_g, self.is_sequence_parallel)
    ctx.dp_metadata = None  # 恢复
    return y_sp
```

### 数据

| 配置 | batch=32 ms/fwd (fwd) | batch=256 ms/fwd (fwd) |
|------|----------------------|----------------------|
| Baseline dInfer (4 GPU) | 48.13 (204) | 98.92 (234) |
| Vanilla d1t4e4 (4 GPU) | 40.26 (201) | 65.10 (235) |
| TV6 d1t4e4 修复前 (4 GPU) | 46.42 (257) | 47.30 (257) |
| **TV6 d1t4e4 修复后 (4 GPU)** | **47.66 (234)** | **49.18 (255)** |

修复前 fwd=257（所有 batch 都一样）→ 修复后 fwd=234（回归正常）：fallback 路径输出不完整导致 decoder 置信度低 → 需要更多迭代。修复后全 256 experts 贡献正确 → decoder 更快收敛。

batch=32 GSM8K，三组对比（Baseline / TV6 d1t4e4 / TV6 d2t4e8）：

## 实验 6: Baseline No-Cache 模式

### 设计动机

测试 baseline 在无 KV cache（BlockDiffusionLLMAttnmask）模式下的性能，作为额外 baseline 数据点。

### 实现

baseline 的 `BlockDiffusionLLMAttnmask` 有 `assert prompt.shape[0] == 1`，不支持 batch>1。在 bench 脚本中 monkey-patch `batched_generate()` 函数替代原始 `generate()`：
```python
def batched_generate(dllm_obj, prompt, gen_length=256, block_length=32):
    batch_size = prompt.shape[0]
    bd_attn_mask = ...unsqueeze(0).repeat(batch_size, 1, 1)  # 原版只 unsqueeze(0)
    pos_ids = ...unsqueeze(0).repeat(batch_size, 1)           # 原版只 unsqueeze(0)
    ...
    if torch.all(decode_compl):  # 原版只 if decode_compl
        break
```

### 命令

```bash
conda run -n dllm_base torchrun --nproc_per_node=4 \
    codex_coding/src/bench_baseline_dinfer.py \
    --batch-size {32,64} --gen-length 256 --num-runs 2 --no-quality \
    --prompt-source gsm8k --pad-to 128 --no-cache
```

### 数据

| batch | fwd | ms/fwd | e2e (s) | vs cache |
|-------|-----|--------|---------|----------|
| 32 | 208 | 77.43 | 16.11 | +60.9% 慢 |
| 64 | 209 | 148.07 | 30.95 | +202% 慢 |
| 256 | — | OOM (28.78 GiB) | — | — |

### 结论

No-cache 模式每步对 prompt+已生成 blocks 做全量 attention（O(batch×seq²)），batch=64 已 3x 慢于 cache，batch=256 OOM（attn mask tensor `[256, total_len, total_len]` 爆显存）。

## 实验 7: SGLang dLLM Benchmark

### 环境搭建过程

**dllm_base 环境（torch 2.8.0）**：sgl_kernel 0.4.2 的 `.so` 有 undefined symbol（C++ ABI 不兼容）。sglang 需要 torch 2.9.1。

**dllm_sglang 环境**：
1. 初始 torch 2.8.0 → sgl_kernel ABI error
2. 升级 torch 2.9.0 → 仍然 ABI error（symbol signature `...jb` vs `...ib`，第 4 参数 unsigned int vs int）
3. 升级 torch 2.9.1 → 仍然 ABI error
4. sgl_kernel 0.4.2.post1 降级到 0.4.1.post1 → 加载成功
5. vllm 0.10.2 + torch 2.9.1 → `std::bad_alloc`（已知问题，见 key_conclusion 2026-04-09）
6. 升级 vllm 0.11.0（`--no-deps`）→ 解决
7. torchvision 0.26（for torch 2.11）不兼容 → 降级到 0.22.1+cu128 → 仍不兼容（`operator torchvision::nms does not exist`）→ 卸载 → sglang 需要它 → 最终由用户重新配好环境

最终可用配置：torch 2.9.1+cu128, vllm 0.11.0, sgl_kernel 0.4.1.post1, sglang 0.5.6.post2（editable install from lib_cite/sglang）。

### 脚本设计

`bench_sglang_dllm.py`：
- `sgl.Engine` 离线模式（子进程 scheduler）
- 支持 `--disable-cuda-graph`, `--attention-backend`, `--max-running-requests`
- deep_gemm.utils.layout stub（sglang 源码版本依赖但环境中缺失）
- threshold 通过 `_sglang_bench_config.yaml` 传入

### Forward 计数方案

SGLang 的 forward 发生在子进程（Scheduler）中的 `LowConfidence.run()` 内部，外部无法直接 hook。

**方案**：在 `lib_cite/sglang/.../low_confidence.py` 加 `_FWD_COUNTER` 全局变量，每次 `model_runner.forward()` 后 `count += 1`，通过环境变量 `SGLANG_FWD_STATS_PATH` 指定的共享文件输出。bench 脚本通过 `prev_fwd` 差值计算每 run 的 fwd count。

### 命令

```bash
# FlashInfer + CUDA Graph ON
conda run -n dllm_sglang python codex_coding/src/bench_sglang_dllm.py \
    --batch-size 32 --gen-length 256 --num-runs 2 --no-quality \
    --prompt-source gsm8k --pad-to 128 --tp-size 4

# FlashInfer + CUDA Graph OFF
同上 --disable-cuda-graph --attention-backend flashinfer

# torch_native (SDPA) + CUDA Graph OFF
同上 --disable-cuda-graph --attention-backend torch_native
```

### 数据（batch=32, GSM8K, pad=128, TP=4）

| attention backend | CUDA Graph | fwd | ms/fwd | e2e (s) | tok/s |
|-------------------|------------|-----|--------|---------|-------|
| flashinfer | ON | ~231* | ~17 | 3.94 | 1767 |
| **flashinfer** | **OFF** | **231** | **40.30** | **9.31** | **748** |
| torch_native (SDPA) | OFF | 236 | 178.36 | 42.09 | 167 |

*CUDA Graph ON 时 graph capture 阶段的 forward 也被计数，导致 fwd count 偏高，ms/fwd 从 e2e/fwd 估算。

### SGLang fwd count 与 dInfer 对比

SGLang LowConfidence (K=8, threshold=0.90) batch=32: **231 fwd**
dInfer Baseline (K=8, threshold=0.90) batch=32: **204 fwd**
差 +13%。可能原因：SGLang 每个 `run()` 调用末尾固定做一次额外 forward（line 92: `out = model_runner.forward(...)`），以及解码算法细节差异。

### SGLang Attention 消融分析

| 因素 | 加速倍数 | 计算方式 |
|------|---------|---------|
| FlashInfer vs torch_native | **4.4x** | 178.36 / 40.30 ms/fwd |
| CUDA Graph | **2.4x** | 9.31 / 3.94 s (e2e) |
| SGLang serving overhead | **~0%** | flashinfer no-graph 40.30 ≈ Our Vanilla 40.26 |

**结论**：SGLang 的 Paged KV 架构依赖 FlashInfer kernel 才高效。用 torch_native SDPA 时反而比 dInfer baseline 慢 3.7x（178 vs 48 ms/fwd），因为 page table 间接寻址的 overhead 在 SDPA 中无法被优化。

## 实验 9: dInfer 框架 batch shrinking 机制分析

### 设计动机

调查已完成请求是否能提前退出计算，理解 fwd count 的含义。

### select_undecoded 分析

```python
def select_undecoded(seq_idx, orig_x, x, block, block_loc, mask_id, writeback=False):
    bool_idx = torch.all(block != mask_id, dim=1)  # 哪些序列已完成当前 block
    if writeback:
        orig_x[finished_idx, block_loc.start:block_loc.end] = block[bool_idx]
    return seq_idx, x  # ← 直接返回，不做过滤！
```
调用侧（line 263-268）预留了 shrink 接口（`if len(seq_idx) == 0: break`），但 `select_undecoded` 永远返回完整 batch。

**原因**：KV cache 是 `[num_layers, 2, batch, heads, max_len, dim]` 连续 tensor。缩 batch 需同步缩 cache + attn_mask + pos_ids + 维护 seq_id mapping。实现复杂度高，且可能破坏 CUDA Graph。

### Block-level early stop 机制

```python
# block decode 结束后 (line 287-289)
eos_idx = torch.any(orig_x[:, block_loc.start:block_loc.end] == decoder.eos_id, dim=1)
if self.early_stop:
    orig_x[eos_idx, block_loc.end:] = decoder.eos_id  # 后续位置全填 EOS
```
已生成 EOS 的序列，后续 block 全是 EOS（非 MASK），while 循环不执行（0 个 MASK）。但这些序列**仍然在 batch 中参与 model forward**（tensor 未缩减）。

### 已完成序列的完整生命周期追踪

假设序列 2 在 block3 生成 EOS，进入 block4 时：
1. `block` tensor `[batch, 32]`：序列 2 全是 EOS（非 MASK）
2. while 条件：其他序列有 MASK → 进入循环
3. `model(block.clone(), ...)` ：序列 2 的 EOS tokens 完整流过 Embedding → Attention → MoE → LM Head
4. `decoder.decode(logits, ...)`：`mask_index = (block == mask_id)` → 序列 2 全 False → 不修改
5. 下一步循环：序列 2 继续陪跑

**结论**：每次 forward 的 batch_size 固定，fwd count × batch_size = 总 forward 计算量。

### 跨框架对比

| 框架 | Block 间 shrinking | Block 内 shrinking | 机制 |
|------|-------------------|-------------------|------|
| dInfer naive_batching | ❌ | ❌ | 全程固定 batch |
| dInfer dynamic_batching | ✅（per-seq 异步调度） | ❌ | mini_batch_size 选 seq |
| Fast-dLLM | ✅（物理缩减 batch + KV cache slice） | ❌ | `input_ids[~finished_flag]` + `past_key_values.key_cache[layer][~finished_flag]` |
| SGLang | ✅（请求级调度 + page KV 释放） | ❌ | `req.finished()` → `release_kv_cache(req)` |

## 已排除的方向

| 方向 | 结果 | 原因 |
|------|------|------|
| Baseline TP=8 | crash | kv_heads=4 不够被 8 整除，SdpaAttention view shape mismatch |
| Baseline batch=512 prefix cache | OOM | logits.float() 需 19.19 GiB（无 OPT-2） |

| SGLang fa3 backend for dLLM | crash | FlashAttention3 不支持 ENCODER_ONLY bidirectional attention |
| SGLang fa2 backend | 不存在 | SGLang 0.5.6 没有 fa2，只有 fa3/fa4/flashinfer/torch_native/triton |
| 迁移 Fast-dLLM batch shrinking 到 dInfer | 不做 | KV cache 是 6D 连续 tensor，batch 维 slice 需 ~29 GiB memcpy |
| TV6 d1t4e4 跳过 dispatch/combine | crash | 每个 rank 只有 N/4 SP tokens，expert_map 指向其他 rank 的 experts |
