## 2. vllm 0.10.2 vs 0.11.0 的 AllToAll 机制差异

### vllm 0.10.2 (NaiveAll2AllManager)
- 后端名：`naive`
- dispatch: `naive_multicast` = 逐 rank broadcast（dp_size 次 broadcast/tensor × 2 tensor = 4 次 NCCL）
- combine: `all_reduce` + CPU slice（1 次 NCCL）
- dispatch 接口：`dispatch(hidden_states, router_logits)` — 只接受 2 个 tensor
- 总计：6 NCCL calls/layer × 19 = 114/forward

### vllm 0.11.0 (AgRsAll2AllManager)
- 后端名：`allgather_reducescatter`
- dispatch: `dp_group.all_gatherv([hidden, router_logits])` — 1 次 NCCL
- combine: `dp_group.reduce_scatterv(output)` — 1 次 NCCL
- dispatch 接口：`dispatch(hidden_states, router_logits, is_sequence_parallel=False)` — 仍只接受 2 个 tensor
- 但 `dp_group.all_gatherv` 本身可以接受任意 tensor list
- 总计：3 NCCL calls/layer × 19 = 57/forward（含 TP all_reduce）
- ★ 需要 ForwardContext 中的 `dp_metadata.sp_local_sizes(sp_size)` 上下文才能工作

### 升级兼容性
- vllm 0.11.0 requires torch==2.8.0 ✓（和我们当前环境兼容）
- 需要 `sys.modules['deep_ep'] = None` 屏蔽 DeepEP 的 NCCL 符号不兼容问题（ncclTeamWorld undefined）
- 缺少 E=32 的 auto-tuned MoE kernel config（WARNING 但不影响正确性）

## 4. 方案 3 设计：S_mask-Aware Route-Before-Dispatch

### 核心原理

利用 Insight A（S_mask 在 M-skip 窗口内完全静态，Jaccard=1.0）：
- **Skip path (77%)**：S_mask 已缓存且不变 → routing 是 per-token 操作 → 可以在本地 256 tokens 上提前 routing → 只广播 hidden + topk 结果（而非 router_logits）
- **Cold/Update path (23%)**：S_mask 需要从 popularity（跨 token 聚合统计）重新计算 → 必须先 dispatch 再 routing

### 为什么需要 S_mask 才能 route-before-dispatch？
- `fused_routing` 本身是 per-token 的（每个 token 独立选 top-4 expert）
- 但 S_mask 的 **计算** 需要跨 token 的 popularity 统计（cold path: K_A kernel 做 atomic 累加）
- 如果只在本地 256 tokens 上计算 popularity → S_mask 可能和全量 512 tokens 不同 → 两个 DP rank 的 S_mask 不一致 → 错误
- **Skip path 绕过了这个问题**：S_mask 是 cold path 在 gathered 512 tokens 上算好的，cached 后所有 rank 共享同一个 S_mask
- **AR MoE 不可能做到**：每步 routing 都变，不存在 "skip 窗口"

### EB 三条路径对 S_mask 的影响

| 路径 | 时机 | |S_mask| | S_mask 内容 | 占比 |
|------|------|---------|------------|------|
| Cold | 新 block 第一次 fwd (N > prev_N) | 新算（actual_s，由 quality 约束决定） | 全新（完整 batch-add 流程） | 3.4% |
| Hot-Update | block 内每 skip_m 步 (fwd_in_block % 5 == 0) | = cold 的 K_init（不变） | 小幅刷新（当前 popularity re-rank） | 19.3% |
| Skip | block 内其余步 | 不变 | 不变（Jaccard=1.0） | **77.3%** |

### 方案 3 实现策略

```
SparseMoeBlock.forward:
  shared_experts(hs_flat)
  router_logits = gate.get_logits(hs_flat)
  
  if will_be_skip(layer_id, N):
    # ★ SKIP PATH: route-before-dispatch
    s_mask = ctrl.get_s_mask(layer_id, router_logits, bias)  # 返回 cached，零计算
    topk_w, topk_ids = fused_routing(router_logits, s_mask, K=4)  # 本地 256 tokens
    g_hs, g_tw, g_ti = dp.all_gatherv([hs_flat, topk_w, topk_ids])  # 广播 routing 结果
    y = fused_experts(g_hs, w13, w2, g_tw, g_ti, expert_map=...)
    y = dp.reduce_scatterv(y)
    y = tensor_model_parallel_all_reduce(y)
  else:
    # COLD/UPDATE: 原路径不变
    y = _moe_forward_with_context(experts, hs_flat, router_logits)
```

## 5. 方案 3 实现中遇到的问题

### 问题 1：skip path 中的 `set_forward_context` 开销

skip path 需要手动调用 `set_forward_context(num_tokens=N)` 来提供 `dp_metadata`（dispatch/combine 依赖）。但 `DPMetadata.make` 内部做了一次 `dist.all_reduce` 来同步各 rank 的 token 数。这导致 skip path **每层额外增加 1 次 NCCL all_reduce**。

19 层 × 1 次 × 每个 forward = 19 次额外 NCCL 调用。加上原有的通信，可能导致 NCCL 调度阻塞或严重变慢。

**现象**：bench_scheme3_dp2.py 在 generate() 循环中运行极慢（看起来像卡住，但实际可能只是慢了 10-50x）。

**潜在解决方案**：
- 预缓存 dp_metadata（cold path 时记录，skip path 复用，避免每层 all_reduce）
- 或在 skip path 中不走 `set_forward_context`，而是直接调用 `dp_group.all_gatherv` 并手动传入 sizes

### 问题 2：单层 model forward 测试通过，generate() 循环卡住

- 单层 MoE forward 测试（batch=16, seq=32, 6 次 forward）：全部通过，cold/skip 切换正确，内存稳定
- 完整 generate() 循环（batch=512, gen=256）：极慢或卡住

**根因分析中**。可能的原因：
1. set_forward_context 的额外 all_reduce 累积
2. cold 和 skip path 之间的 NCCL collective 序列不一致导致隐性死锁
3. E=32 缺少 auto-tuned config 导致 fused_experts kernel 显著变慢

## 6. Sequence Parallelism 分析（新方向）

在分析 vllm 0.11.0 的 AgRs 后端时发现：C12 的 TP group 内 4 个 GPU 在 gate + routing + shared_expert 上存在 **3/4 冗余**（4 个 GPU 计算完全相同的结果）。

Sequence Parallel（类似 Megatron-LM 的 SP）可以消除这个冗余：
- 把 Attention 的 AllReduce 拆成 ReduceScatter + AllGather
- MoE 的 gate + routing + shared 只处理 1/4 tokens → 4x 减少
- 预估收益 ~9%（比方案 3 的 ~2-3% 更大）
- 但实现复杂度更高（需要改 attention 输出和 MoE 输入/输出）
- 和方案 3 正交，可叠加
