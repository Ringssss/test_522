# v0.1.10-IterSmooth 与 VicinityCache 修复、性能对比与 BD+IterSmooth 结合方案

## Goal

修复 IterSmooth 和 VicinityCache 在 LLaDA2MoE 上的兼容 bug，测试修复后能否超过当前 SOTA baseline（BD-attnmask 75-77 tok/s），并设计 IterSmooth 与 BD 的结合方案。

## Changes Made

### Bug 修复

1. **IterSmooth dtype bug**（`modeling_llada2_moe.py:284`）：
   - `prob @ self.W_e` 中 prob 是 float32（softmax 输出）而 W_e 是 bfloat16（模型权重）
   - 修复：`prob.to(self.W_e.dtype) @ self.W_e`

2. **VicinityCache position_ids + replace_position bug**（`generate_uniform.py:704-707` 和 `795-801`）：
   - `DiffusionKVCacheManager.get_key_values` 对 prefix 类型返回 `replace_position = (left_start, seq_len)`，其中 seq_len 是全 cache 长度，不是窗口右边界
   - 导致模型内部推导出的 position_ids 长度和实际窗口输入不匹配 → RoPE size mismatch
   - 同时 replace_position 传到 attention 层的 KVCache.update 时，slice_scatter 的 src 和 slice 尺寸不匹配
   - 修复：在 VicinityCacheIteration.forward 和 IterSmoothWithVicinityCacheIteration.forward 中，覆盖 replace_position 为窗口范围 `(left_start, right_end)`，并显式传入 `position_ids`

## Key Conclusions

1. **IterSmooth 和 VicinityCache 在 BW 框架下均无法超过 BD-attnmask baseline**
2. **IterSmooth 在 BW+长 prompt 下反而大幅增加 forward 次数**（80→102），soft embedding 让模型更困惑
3. 原因：BW 框架让模型看到未来全 mask block，IterSmooth 给这些噪声位置也算了 soft embedding → 污染信息
4. **VicinityCache 没有减少 forward 次数**（80→80），窗口化 KV 管理开销反而拖慢了 fwd/s
5. **根本瓶颈不变**：BW 系列的 forward 次数（62-102）远多于 BD（48），这个差距来自 BW 让模型看到未来 mask block

## 提出的下一步方案：BD + IterSmooth 结合

核心思路：在 BD-attnmask 的 no-cache 路径上引入 IterSmooth 的 soft embedding，但只对当前 block 内的 mask 位置做 soft embedding，不影响 prompt 和已完成 block。

关键设计：
- 用 `inputs_embeds` 代替 `input_ids` 送入模型
- prompt + 已完成 block 的 embedding 始终是 discrete（标准 word embedding）
- 只有当前 block 内的 mask 位置用 soft embedding（`prob @ W_e` 加权混合）
- `h2e` 的计算量从 O(total_len × V × d) 降到 O(block_len × V × d)
- 保留 BD 的 block-causal attention mask
- 引入 threshold_decay（前几步更保守，后几步放松）

实现方式：新建 `IterSmoothBlockDiffusionLLMAttnmask` 类（约 80 行），不修改任何现有类。
