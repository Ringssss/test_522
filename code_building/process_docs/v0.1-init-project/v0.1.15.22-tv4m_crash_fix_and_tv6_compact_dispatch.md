# v0.1.15.22 — TV4m Crash 修复 + TV6 Compact Dispatch/Combine

## 主题

TV4m（mapped Triton kernel + compact cache）的 crash 修复、正确性验证、以及 TV6（compact dispatch/combine + vllm 原版 kernel）的完整设计、实现、profiling 和 CPU overhead 优化。

## 动机

上轮 (v0.1.15.21) 实现了 TV4m（自定义 Triton kernel `_fused_moe_kernel_mapped`，加 input_map 参数间接寻址从 FULL A 读取），理论可达 -16% vs G，但 crash（illegal memory access）。本轮目标：(1) 修复 TV4m crash 并验证质量，(2) 探索 TV6 compact dispatch/combine 路线。

## 实验记录

### 实验 1: TV4m Crash 修复 — Padding OOB + C Stride + B Stride

**设计动机**：修复 `_fused_moe_kernel_mapped` 的 crash。从 crash 信息 "illegal memory access" 和 "misaligned address" 入手。

**Bug 1: sorted_token_ids padding sentinel 越界 input_map**

`moe_align_block_size` 输出的 sorted_token_ids 对齐到 BLOCK_SIZE_M，padding sentinel = `num_valid_tokens`。`compact_tok = offs_token // top_k` 对 sentinel 值越界 input_map（长度 N_compute）。

修复：
```python
max_row_idx = tl.maximum(num_valid_tokens // top_k - 1, 0)
compact_tok = tl.minimum(offs_token // top_k, max_row_idx)
```

**Bug 2: C tensor stride 错误**

vllm 对 3D C (M, top_k, N) 传 `C.stride(1), C.stride(2)`（跳过 dim-0），但 TV4m 传了 `C.stride(0), C.stride(1)`。`sorted_token_ids` 是 flat M*top_k 索引，kernel 用 `c_ptr + stride_cm * offs_token`。如果 stride_cm = C.stride(0) = top_k*N，offs_token 到 M*top_k-1 时偏移远超 buffer 大小。

修复：
```python
C_flat = C.view(-1, C.size(-1)) if C.ndim == 3 else C
# stride_cm = C_flat.stride(0) = N (正确)
```

确认来源：vllm `invoke_fused_moe_kernel` line 638-639 传 `C.stride(1), C.stride(2)`。

**Bug 3: B weight stride 顺序反了**

vllm 传 `B.stride(0), B.stride(2), B.stride(1)`（对应 stride_be, stride_bk, stride_bn），因为 B 存储格式是 (E, N, K)。TV4m 传了 `B.stride(0), B.stride(1), B.stride(2)`，K/N 维度搞反。

修复：
```python
B.stride(0), B.stride(2), B.stride(1),  # stride_be, stride_bk, stride_bn
```

**修复后首次运行**：从 "illegal memory access" 变为 "misaligned address"，再到运行成功但质量崩坏。

**命令**：
```bash
DINF_SKIP_LOGITS_FLOAT=1 DINF_SP_LM_HEAD=1 torchrun --nproc_per_node=8 bench_bsp_moe_dp2.py \
  --config-set team_tv4m --profile-target bsp --batch-size 512 --gen-length 256 --num-runs 1 --no-quality
```

**数据**：
| 阶段 | ms/fwd | Forward | Path counts | 质量 |
|------|--------|---------|-------------|------|
| 修复前 | crash | — | — | crash |
| Bug 1+2+3 修复后 | 57.61 | **485** | 19/171/**7296**/**1729** | ✗ 崩坏（重复词，forward 数 2x） |

### 实验 3: Dump 真实数据 → Standalone 复现

**设计动机**：kernel 合成数据 PASS 但 bench 脚本 FAIL → 问题在传入参数。dump 真实 tensor 到 standalone test 精确复现。

**实现**：在 bench 脚本 debug 点 dump hs_g、w13_weight、input_map、sorted_token_ids 等到 `/tmp/tv4m_debug/`。

**数据**：
```

w13: shape=[32, 1024, 2048]                       ← B.size(1)=1024 才是正确的 N
```

**发现 Bug 5 (ROOT CAUSE)**：
```python
N = exp_obj.w13_weight.shape[2]  # = 2048（K 维度，错！）
# 应为：
N = exp_obj.w13_weight.shape[1]  # = 1024（N 维度，输出维度）
```

**因果链**：
```
N=2048（错）
→ intermediate_cache1 = (3890, 4, 2048)
→ kernel 写 B.size(1)=1024 列 → 后 1024 列未初始化
→ silu_and_mul(cache2, cache1.view(-1, 2048))
  → 取前 1024 列 silu × 后 1024 列（垃圾）
→ 质量崩坏（forward 数 2x，重复词）
```

### 实验 12: TV6 v4 — 消除隐式 GPU→CPU Sync

**设计动机**：nsys gap 分析显示 200μs-1ms gap 暴增 10x（8699 vs 795）。排查发现 boolean indexing 内部调 `.nonzero()` 触发 per-layer 隐式 sync。

**隐式 sync 来源**：
1. `hidden_states[compute_mask_sp]`（boolean indexing → 内部 .nonzero() → sync）— **per layer × 19**
2. `router_logits[compute_mask_sp]`（同上）— **per layer × 19**
3. `[c.item() for c in gathered_counts]`（8 次 .item() → 8 次 sync）— per forward

**修复**：
```python
# boolean indexing → integer indexing (no sync)
compute_idx_sp = _tv6_compute_indices_sp[0]  # 已在 model_forward 计算
hs_compute_sp = hidden_states[compute_idx_sp]  # int index → no sync!
rl_compute_sp = router_logits[compute_idx_sp]

# 8× .item() → 1× .tolist() (1 sync instead of 8)
compact_sizes = torch.cat(gathered_counts).tolist()
```

**数据**：
| Config | Run 1 | Run 2 | 平均 | vs G |
|--------|-------|-------|------|------|
| G | 59.34 | 58.84 | 59.09 | — |
| TV6 v3 (sync 优化前) | 61.18 | 60.62 | 60.90 | +2.8% |
| **TV6 v4 (sync 优化后)** | **59.32** | **58.72** | **59.02** | **-0.1%** |

**结论**：消除隐式 sync 后 **-1.88 ms/fwd**。TV6 从 +2.8% 追到和 G 基本持平。

### 实验 13: TV6 v5 — In-Place Cache

**设计动机**：per-layer cache merge 仍有 3 个 kernel（index_select + index_copy + clone）。分析数据依赖后发现可以直接修改 cache tensor。

**正确性分析**：
- null mask 单调递增（decoded token 不会变回 mask）
- 一旦某位置变成 null，cache 中的值是"上一次被计算时的输出"
- 直接 `y_sp = _tv6_moe_cache[lid]` 引用 cache，`index_copy_` 只覆盖 compute 位置
- null 位置自然保留上一步的 cached 值
- 下游 `y_sp + shared_res` 创建新 tensor（不修改 cache），stream 顺序保证安全

**实现**：
```python
# 当前（4 kernel/layer）：
y_sp = bufs['y_sp']
torch.index_select(cache[lid], null_idx, out=buf_cached)
y_sp.index_copy_(null_idx, buf_cached)
y_sp.index_copy_(compute_idx, y_compute_sp)
_tv6_moe_cache[lid] = y_sp.detach().clone()

# 优化后（1 kernel/layer）：
y_sp = _tv6_moe_cache[lid]  # 直接引用 cache
y_sp.index_copy_(0, compute_idx, y_compute_sp)  # 只写 compute 位置
```

**数据**：
| Config | Run 1 | Run 2 | 平均 | vs G |
|--------|-------|-------|------|------|
| G | 59.33 | 58.83 | 59.08 | — |
| TV4m | 58.39 | 57.84 | 58.12 | -1.6% |
| TV6 v4 (sync 优化) | 59.32 | 58.72 | 59.02 | -0.1% |
| **TV6 v5 (in-place cache)** | **58.70** | **57.96** | **58.33** | **-1.3%** |

**质量验证**：
```
#0:  Let's solve each problem step by step.                    ✓
#8:  Let's solve the quadratic equation:                       ✓
#13: Let's solve this logic puzzle step by step.               ✓
#19: ...n-th Fibonacci number using iterative approach...      ✓
#28: ...8 planets in our solar system...                       ✓
```
path counts 19/171/3933/931 ✓

**结论**：In-place cache 省 -0.7 ms/fwd。TV6 达到 -1.3% vs G，接近 TV4m 的 -1.6%。

## 总结

2. 回移 sync 优化 + in-place cache 到 TV4m
3. native 集成（消除 Python overhead，兑现 TV6 的 -28.2s GPU 端节省）
