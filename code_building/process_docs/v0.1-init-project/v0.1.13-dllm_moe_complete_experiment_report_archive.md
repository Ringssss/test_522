## 核心成果

### 1. 三个 Insight 的完整量化验证

**Insight A: MASK token routing 集中**
- 浅层 MASK entropy 仅为 decoded 的 65%
- 浅层仅激活 64-76/256 experts
- Gini 系数 > 0.93（极度不均衡）
- 跨设置稳健（batch=1/8/32, temp=0/0.7）

**Insight B: 跨迭代 MoE 计算冗余**
- 已解码位置 routing change rate 仅 ~24%
- MoE output cosine similarity 0.97-0.99
- 总冗余率：batch=1 30%, batch=8 49%, batch=32 52%
- 冗余率随迭代单调递增（iter 0: 0% → iter 15: 58.7%）

**Insight C: 天然批量效应**
- dLLM batch=1 处理 32 tokens（AR 需 batch=32）
- 天然更能喂饱 GPU
- 但 per-expert GEMM 仍极小（memory-bound）

### 2. Stable Cache 优化的系统性失败

**尝试路径**：
- v1: 缓存 full MoE output → 失败
- v2a: 只缓存 routed，shared 始终新鲜 → 失败
- v2b: 加周期性刷新 (N=2) → 失败
- v2c: 排除敏感层 L18 → 失败

**关键发现**：
- 单层 ablation safe ≠ 多层组合 safe
- 误差通过 attention 跨层传播累积
- 根本矛盾：跳过计算 ↔ 保持 cache fresh 不可兼得

### 3. Padding-Free MoE Kernel 优化尝试

**实现**：
- 基于 X-MoE (SC 2025) PFT 方案
- 完整 padding-free pipeline（dispatch + gather + grouped GEMM + scatter）
- 正确性验证：cosine sim = 0.999994

**性能结果**：
- batch=1: 0.84ms vs baseline 0.53ms（**慢 1.58x**）
- batch=32: 1.22ms vs baseline 0.80ms（慢 1.53x）

**根因分析**：
- 瓶颈是 expert weight HBM loading，不是 padding compute
- Per-expert GEMM 算术强度 ~1.5 MAC/byte（H100 平衡点 ~295）
- 完全 memory-bound，padding 的额外计算几乎免费
- vllm kernel 有 H100 专用 autotuning，我们的 grouped GEMM 缺少

## 关键结论

1. **三个 Insight 作为 observation 贡献成立**，在所有测试设置下稳健，量化了 dLLM MoE 与 AR MoE 的根本差异

2. **直接"跳过计算"的优化路径有根本性困难**：
   - Stable cache 因误差累积失败
   - Padding-free kernel 因 memory-bound 特性无法超越 baseline

3. **仍然有效的优化方向**：
   - 减少 forward 次数（IterSmooth 已验证 -12.8%）
   - 多卡 EP 场景下 Insight A+B 的影响被放大
   - 借鉴 EARTH 的分层/渐进思想

4. **对于 LLaDA2.0-mini（256 experts, intermediate=512）在 H100 上**：
   - MoE kernel 瓶颈是 weight loading 带宽，不是 padding compute
   - 消除 padding 无法超越已高度优化的 vllm baseline
