# v0.1.15.12k — BSP-MoE nsys Collective Profiling

## Goal

在 BSP-MoE 机制验证之后，用 Nsight Systems 继续定位：

1. 为什么 BSP 理论上减少了 TP 内 MoE token 冗余，但 wall-clock 收益很小。
2. AgRs `combine` 和新增 TP `all_gather` 是否吃掉了收益。
3. BSP 是否确实减少了其他开销，例如 D2D memcpy、dense GEMM 或 MoE wrapper 时间。

本轮不继续修改 dInfer/vLLM 源码；只增加可复现的 nsys sqlite 分析脚本和报告。

本轮使用的是短 nsys trace，不是完整 C12 `batch=512,gen=256` trace。原因是 nsys sqlite 已经达到 200MB 级别，短 trace 足够先定位 kernel/collective 序列。

## E2E And Generate Window

短 trace 下 BSP 明显变慢：

| Metric | A baseline | B BSP | B vs A |
|---|---:|---:|---:|
| log time | 4.176s | 4.680s | +12.07% |
| log ms/fwd | 69.60 | 76.72 | +10.23% |
| NVTX rankmax generate | 3895.928 ms | 4406.343 ms | +13.10% |

解释：

- nsys 有 profiling overhead，绝对 ms/fwd 不应和无 profiling e2e 混比。
- A/B 在同一 nsys 条件下对比，方向可信：BSP 短 trace 更慢。

## NVTX Component Summary

短 trace 的外层 MoE wrapper NVTX 显示：

| Component | A rankmax ms/fwd | B rankmax ms/fwd | B vs A |
|---|---:|---:|---:|
| moe.shared | 3.470 | 4.024 | +15.97% |
| moe.gate_logits | 2.270 | 2.106 | -7.24% |
| moe.native_forward | 35.251 | 27.389 | -22.30% |
| moe.bsp_chunk | n/a | 0.584 | n/a |
| moe.tp_all_gather | n/a | 3.216 | n/a |

可见：

- `moe.native_forward` 外层时间下降，说明 BSP 的 SP-native MoE 路径确实减少了一部分 MoE 内部工作。
- 但新增的 `moe.tp_all_gather` 本身就约 `3.216 ms/fwd`。
- `shared` 在 BSP 里没有变快，说明当前 monkey-patch 的局部切分并没有稳定兑现 shared expert 的理论节省，可能受 layout、collective 等待或 CPU/NVTX range 包含范围影响。

## Kernel Category Summary

按 CUDA kernel 名称分类后，关键变化如下：

| Category | A rankmax ms/fwd | B rankmax ms/fwd | B vs A |
|---|---:|---:|---:|
| NCCL kernels | 7.993 | 17.114 | +114.12% |
| vLLM cross_device_reduce | 16.276 | 4.687 | -71.20% |
| dense GEMM | 0.441 | 0.213 | -51.74% |
| MoE fused kernel | 1.147 | 1.110 | -3.20% |
| routing/topk | 0.160 | 0.158 | -1.78% |
| attention | 0.174 | 0.173 | -0.42% |

解释：

- BSP 确实减少了一些 dense GEMM/D2D 类开销。
- 但 MoE fused kernel 时间几乎不变，符合此前 “fused_moe memory-bound，active expert/weight loading 才是瓶颈” 的判断。
- 最大新增开销来自 NCCL，总 rankmax ms/fwd 翻倍以上。

## Collective Split

collective 拆分是本轮最关键证据：

| Collective | A count | A rankmax ms/fwd | B count | B rankmax ms/fwd | B vs A |
|---|---:|---:|---:|---:|---:|
| NCCL_Reduce | 9120 | 2.381 | 9272 | 7.573 | +218.05% |
| NCCL_AllGather | 9120 | 1.837 | 18392 | 5.962 | +224.53% |
| NCCL_AllReduce | 9624 | 3.768 | 9784 | 4.648 | +23.35% |
| vLLM_cross_device_reduce | 18720 | 16.276 | 9760 | 4.687 | -71.20% |
| NCCL_Broadcast | 472 | 0.266 | 632 | 0.248 | -6.85% |

核心判断：

- BSP 把一部分 baseline 中的 vLLM cross-device TP reduce 降下来了。
- 但是它显著增加了 NCCL `AllGather` 和 `Reduce`。
- `AllGather` count 近似翻倍：baseline `9120`，BSP `18392`。这和 BSP 路径“native AgRs dispatch 的 all-gather + 显式 TP all-gather 输出收集”一致。
- `NCCL_Reduce` 单次/总耗时明显放大，对应 AgRs combine/reduce-scatter 侧压力增加。

## Source-Level Explanation

vLLM AgRs all2all 的实现关键点：

- 文件：`/home/wuhang/miniconda3/envs/dllm/lib/python3.10/site-packages/vllm/distributed/device_communicators/all2all.py`
- `AgRsAll2AllManager.dispatch/combine` 中：
  - `is_sequence_parallel=False` 时使用 `get_dp_group()`
  - `is_sequence_parallel=True` 时使用 `get_ep_group()`

这解释了 BSP 的 collective 变化：

| Path | AgRs group | Extra step |
|---|---|---|
| Baseline | DP group | FusedMoE 后做 TP all-reduce |
| BSP | EP group | FusedMoE sequence-parallel combine 后，再显式 TP all-gather 还原 token |

因此 BSP 的问题不是理论方向错误，而是当前路径把 MoE token 冗余转移成了更重的 collective sequence。

## Conclusion

本轮 nsys 结论：

1. BSP 的“减少工作量”是存在的：D2D memcpy 下降约 48%，dispatch payload 在完整 C12 timing 中下降 75%，dense GEMM 也下降。
2. 但是当前 monkey-patch 路径的 NCCL 开销明显放大：NCCL rankmax ms/fwd `7.993 -> 17.114`，AllGather 和 Reduce 都超过 `+200%`。
3. AgRs combine 变慢不是偶然噪声：短 nsys trace 的 NCCL Reduce/AllGather 放大，与完整 C12 component timing 中 `moe.combine 3.587 -> 8.284 ms/fwd` 对齐。
4. 继续在 Python monkey-patch 层叠加 Scheme3 等小优化意义不大；应该优先解决 collective layout。

## Next Technical Direction

优先方向应从“再省一点 router/gate payload”转为“让 BSP 不额外制造昂贵 collective”：

| Direction | Why |
|---|---|
| 原生 BSP/SP MoE integration | 避免 Python wrapper、重复 context、外层显式 TP all-gather 和 AgRs group 切换副作用 |
| combine/gather 融合或重排 | 当前新增 TP all-gather 与 AgRs combine 是主要 blocker，应尝试把最终 token gather 与 combine/reduce-scatter 融合或延迟 |
| 保持 MoE 输出 sequence-parallel 更久 | 如果后续层可接受 SP layout，就不用每层 MoE 后立刻 all-gather 成完整 `[N,h]` |
| 谨慎耦合 Scheme3 | 只有在 collective overhead 降下来之后，Scheme3 的 routing-logits 节省才可能被看见 |
