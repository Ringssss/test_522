Source-level explanation:

- vLLM `AsyncTPPass` replaces `aten.mm -> torch.ops.vllm.reduce_scatter` with `torch.ops.symm_mem.fused_matmul_reduce_scatter(..., "avg", scatter_dim=0, ...)`.
- Current eager `tensor_model_parallel_reduce_scatter` uses NCCL `ReduceOp.SUM`.
- Therefore directly compiling our current attention O-proj `GEMM -> reduce_scatter(sum)` with this pass would scale the result by `1/tp` and is not safe.

Conclusion:

- The dInfer-owned adapter route is viable and maximally reuses vLLM's compile backend/pass/kernels.
- `AllGather -> GEMM` is the safe first AsyncTP integration candidate.
- `GEMM -> ReduceScatter` must not be landed into BSP-G attention output until the sum/avg semantic mismatch is solved, either by a safe compensation path or by a vLLM/source-level sum variant.
- No EB/s_mask, Scheme3 payload, MoE routing, or topology behavior was changed.

## Phase S4b - DInferCompileBackend Fused-Sum Validation

**Status:** planned

### Goal

Validate whether the raw PyTorch symmetric-memory op supports `GEMM -> ReduceScatter` with SUM semantics:

```python
torch.ops.symm_mem.fused_matmul_reduce_scatter(
    x, w, "sum", scatter_dim=0, group_name=tp_group_name)
```

This decides whether dInfer can build a dInfer-local AsyncTP SUM pass while still reusing vLLM/Inductor infrastructure.

### Why This Phase Exists

Previous S4 proved:

- vLLM AsyncTP pattern-hit works in this environment.
- `AllGather -> GEMM` fused path is semantically exact vs eager.
- `GEMM -> ReduceScatter` fused path is not safe for dInfer today because vLLM replacement uses `"avg"`, while dInfer/vLLM eager `tensor_model_parallel_reduce_scatter` is SUM.

Source evidence:

- vLLM `GEMMReduceScatterPattern.replacement` hardcodes `"avg"`.
- Torch/Inductor fused-matmul-RS API carries a `reduce_op` string, and Torch micro-pipeline code passes through `reduce_op`, so `"sum"` is a plausible raw-op mode that must be measured rather than assumed.

### AsyncTP Source Check

Installed vLLM source facts:

- `PostGradPassManager.configure()` adds `SequenceParallelismPass` when `pass_config.enable_sequence_parallelism` is true, and adds `AsyncTPPass` when `pass_config.enable_async_tp` is also true.
- vLLM's `SequenceParallelismPass` explicitly says it transforms `AllReduce -> RMSNorm` into `ReduceScatter -> local RMSNorm -> AllGather`, and mainly lays groundwork for later fusion.
- `AsyncTPPass` registers:
  - `GEMM + vllm.reduce_scatter -> symm_mem.fused_matmul_reduce_scatter`
  - `vllm.all_gather + GEMM -> symm_mem.fused_all_gather_matmul`
  - scaled/fp8/cutlass variants for bf16-compatible paths.
- AsyncTP only applies when `runtime_shape % tp_size == 0`.
- `enable_async_tp` automatically enables `enable_sequence_parallelism` in `VllmConfig`.
- vLLM filters CUDA graph/capture sizes for SP so sizes must be divisible by TP.

dInfer status:

- Current benchmark/source path calls runtime collectives directly and does not run through vLLM `VllmBackend`.
- Existing dInfer compile path uses ordinary `torch.compile(...)` / sglang compile monkey patch, so it does not inject vLLM `PostGradPassManager`.
- Therefore current BSP-G/GS measurements have not consumed vLLM AsyncTP fusion benefits.

Recommended plan:

1. Keep dp2/tp4/ep8 GS as the valid quality/performance reference. Do not adopt TP8 yet.
2. Add an AsyncTP pattern-hit probe in dInfer using `VllmBackend(VllmConfig(...pass_config.enable_async_tp=True...))` on a minimal compiled module that exposes `mm -> vllm.reduce_scatter` and `vllm.all_gather -> mm`.
3. If pattern-hit is confirmed, compile a narrow production-shaped block first: attention output projection + reduce-scatter. This matches BSP-G's strongest current mechanism.
4. Only after correctness and pattern-hit are stable, test a larger decoder-layer compile path with static token sizes (`N=8192`, `tp=4`, divisible by TP), no forward-time module mutation, and source-level SP metadata.
5. Treat `all_gather -> QKV/GEMM` as a second target. Current conservative G mostly gathers before attention, so exposing the all-gather+GEMM pattern may require the G2-style attention-owned gather boundary.

Answer to the user's question:

- Yes, `4096` was tested.
- No, `4096` does not beat eager in this environment/shape. With native env it is still `~2.3x` slower than eager, and repeated-call semantics are unstable.
- Splitting `8192` into `2 x 4096` does not adapt the workload successfully. It is both semantically invalid under native path and slower than the current eager full `8192` path.

Why this resolves the threshold question:

- The threshold indicates where PyTorch is willing to try `_async_input_mm`, not a guarantee that it beats NCCL+cuBLAS for our QKV shape.
- Our `K=2048,N=768,tp=4,bf16` QKV GEMM is already efficient with cuBLAS after eager all-gather.
- The symmetric-memory route pays barrier/signal/rendezvous and chunked GEMM overhead. At these shapes that overhead dominates.
- Native path also appears unsafe for repeated standalone raw-op use in this benchmark, so it cannot be used as a dInfer source integration basis without deeper PyTorch/kernel debugging.

Final S4e decision:

- Do not adapt 8192 QKV by chunking into `4096`.
- Do not integrate `symm_mem.fused_all_gather_matmul` for BSP-G QKV.
- Keep eager attention-input all-gather + QKV GEMM.
- Move performance focus back to BSP-H/F2 MoE collective/layout redesign.
