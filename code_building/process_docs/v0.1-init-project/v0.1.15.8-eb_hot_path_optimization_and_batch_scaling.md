# v0.1.15.8 — EB 热路径优化 + 大 Batch Scaling 验证

## 1. 本轮目标

在 v0.1.15.7 确立的 C5（fused routing，-12.4% vs C0）基础上，尝试让 Expert Budgeting（EB）叠加后超过 C5。核心挑战：EB 热路径的 K_A+K_B 每层每 forward 的开销（~290μs）超过了 fused_experts 因 S_mask 限制获得的节省（~130μs）。

## 3. K_init 修正 (v0.1.15.8b-c)

### 发现的 Bug

Cold path 结束时设置 `K_init = K_target + MAX_ROUNDS × cap = 40 + 128 = 168`（理论最大值），而非实际 |S|。

Plan A 的 99.9% 零轮 batch-add 是在 **K_init ≈ 103（cold path 实际 |S|）** 的条件下测的。Hot path 应该用 cold path 的实际 |S|，在整个 block 内不变。

### 修正方案

Cold path 末尾：`actual_s = int(b['s_mask'].sum().item())`，存入 `K_init[layer_idx]`。
一次 GPU→CPU sync（仅 cold path，~3μs × 171 冷启动 = 513μs 总开销，可忽略）。

### 实验结果 (gen_length=64, batch=32)

| Config | Time(s) | Fwd | ms/fwd | vs C5 |
|--------|------:|----:|------:|------:|
| C5 | 2.555 | 89 | 28.71 | baseline |
| C10-v1 (K_init=168) | 2.795 | 89 | 31.40 | +10.7% |
| C10-v3 (K_init=actual ~91) | 2.881 | 91 | 31.66 | +12.7% |
| C10-v3 (K_init=|S|+2×cap) | 2.840 | 91 | 31.21 | +12.5% |

K_init 修正让 ms/fwd 略降（fused_experts 更快），但 fwd 从 89 增加到 91（|S| 更紧限制了 routing）。

## 4. K_A Kernel 优化（全部失败）(v0.1.15.8d)

| 变体 | 改动 | Fwd | 结果 |
|------|------|----:|------|
| K_A 原版 (sigmoid + weighted atomic) | — | 91 | baseline |
| K_A_lite v1 (no sigmoid, count-based) | 去 sigmoid，atomic_add(1.0) | 93 | fwd +2，质量降 |
| K_A_lite v2 (no sigmoid, weight-based) | 去 sigmoid，保留 weighted | 92 | fwd +1 |
| K_A_v2 (local_pop accumulation) | BLOCK_N 个 token 累积后统一 atomic | — | 更慢（寄存器压力） |

**结论**：原版 K_A（per-token atomic + sigmoid + normalize）已是最优。sigmoid 对 top-12 选择有实质影响，不能省略。

## 5. K_B_v3 (tl.sort) 验证 (v0.1.15.8e-f)

来源：算法同学方案 `docx/cites/warmstart_triton_final.md`。

### Micro-bench

| Kernel | N=1024 | N=3200 | 说明 |
|--------|------:|------:|------|
| K_B_v2 (iterative argmax) | 72μs | 72μs | 256 次串行 argmax |
| **K_B_v3 (tl.sort)** | **44μs** | **43μs** | tl.sort + threshold + tie-break |
| Speedup | 1.63x | 1.68x | |

正确性：Jaccard = 1.0000（和 Python ref 完全一致）。

### E2E (C10-v6: 原版 K_A + K_B_v3)

| Config | Time(s) | Fwd | ms/fwd | vs C5 |
|--------|------:|----:|------:|------:|
| C5 | 2.542 | 89 | 28.56 | baseline |

K_B_v3 的 tie-breaking 差异导致 +1 fwd，ms/fwd 微降但净效果略负。

**结论**：K_B_v3 在 micro-bench 更快，但 E2E 改善被 fwd 增加抵消。作为最优 kernel 组合保留。

## 8. CUDA Stream Overlap（失败）(v0.1.15.8i)

**脚本**: `test_c10_overlap.py`。用 `torch.cuda.Stream` 把 K_A+K_B 放到 eb_stream 和 fused_experts 并行。

### 结果

| 版本 | Time(s) | Fwd | vs C5 |
|------|------:|----:|------:|
| C5 | 7.778 | 272 | baseline |
| C10-delay (模拟，无 overlap) | 8.728 | 272 | +12.2% |
| C10-overlap v1 (有 .copy_()) | 9.292 | 273 | +19.6% |
| C10-overlap v2 (双缓冲 swap) | 9.023 | 272 | +16.0% |

### 失败原因

fused_experts 是 **memory-bound**（HBM 利用率 86%）。K_A 在 eb_stream 上读 logits 时争抢 HBM 带宽，导致 fused_experts 变慢。ms/fwd 从模拟的 32.09 上升到 33.17-34.04。

消除 `.copy_()` 改用双缓冲指针 swap 省了 ~270ms（修复了隐式 sync），但 HBM 竞争无法通过 Python 层面解决。

**结论**：overlap 方向因 HBM 竞争不可行。

## 10. ★★★★★ HetEval-128 大 Batch 验证 (v0.1.15.8k)

**脚本**: `test_heteval128.py`，128 个异质 prompt，batch=128。

### 核心假设

batch=32 时 unique active experts ≈ 162/256（63%），S_mask |S|≈120 限制效果有限。
batch=128 时 unique active experts ≈ 250/256（98%），S_mask |S|≈160 限制 37.5% 的 experts → 收益更大。

### 结果

| Config | batch | Time(s) | Fwd | ms/fwd | vs C5 |
|--------|------:|------:|----:|------:|------:|
| C5 | 32 | 7.693 | 272 | 28.28 | baseline |
| C10-M∞ | 32 | 7.998 | 274 | 29.19 | **+4.0%** |
| C5 | **128** | **12.412** | **278** | **44.65** | baseline |
| **C10-M∞** | **128** | **12.134** | **285** | **42.57** | **-2.2% ★** |

### 数据分析

- ms/fwd 节省：44.65 → 42.57 = **-2.08ms/fwd (-4.7%)**
- fwd 惩罚：+7 fwd × 42.57ms = +298ms
- 净收益：278 × 2.08 - 298 = **280ms (-2.2%)**
- |S| avg = 160.5, min=118, max=168
- 质量：5/5 PASS
- GPU 显存：32.7GB / 85.0GB（batch=128 可行）

### 关键 Insight

**EB 的收益随 batch size 增长**：
- batch=32: unique expert 减少 ~26% → fused_experts 省 ~14.5% → 不够覆盖 EB 开销
- batch=128: unique expert 减少 ~37.5% → fused_experts 省更多 → 超过 EB 开销

这是一个重要的 **scaling 特性**——生产 serving 场景（大 batch）下 EB 优势更明显。
