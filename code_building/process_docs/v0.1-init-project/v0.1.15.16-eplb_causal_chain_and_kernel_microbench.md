# v0.1.15.16 EPLB 因果链分析与 Kernel Micro-benchmark

## 主题

EPLB 在 EP=8 单节点下为什么只有 ~0.5% 收益？能否找到让它有效的方法？

## 动机

上轮 (v0.1.15.15) 的 I22 实验显示 EPLB per-layer balanced placement 仅改善 0.28-0.36% wall-clock。本轮目标是找到根因——是 memory-bound 抑制、统计平滑、还是 EPLB 实现问题？

## 实验记录

### 实验 1：Grouped Topk 消融

**设计动机**：grouped topk (ng=8, tkg=4) 可能做了隐式负载均衡，掩盖了真实不均衡。去掉它看 CV 是否增大。

**实现**：setup_routing 加 global_topk=False 参数，设 ng=1, tkg=1 退化为全局 topk。

**命令**：
```bash
torchrun --nproc-per-node=8 bench_bsp_moe_dp2.py --config-set global_topk --num-runs 2 --full-quality-output --results-suffix c12_global_topk_ab_20260503
```

**数据**：
| Config | ms/fwd | ep_load_cv | layer_cv_mean |
|--------|--------|-----------|---------------|
| A (grouped) | 80.92 | 0.074 | 0.282 |
| A-GT (global) | 79.75 | 0.071 | 0.276 |
| GS (grouped) | 76.96 | 0.076 | 0.286 |
| GS-GT (global) | 76.31 | 0.072 | 0.278 |

质量：全部正确回答 verifiable prompts，无显著退化。

**结论**：grouped topk 不是隐式负载均衡器。负载 CV 由 32 experts/GPU 的统计平滑决定。

---

### 实验 2：K 值验证

**设计动机**：确认 FusedMoE kernel 实际用的是 K=4（EB 后）还是 K=8（模型 config）。

**实现**：在 setup_routing 的 routing function 中加 shape print。

**数据**：
```
[K-verify #0] layer=0 path=prefill_fallback hs=(49152, 2048) idx=(49152, 4) K_actual=4
[K-verify #1] layer=0 path=cold hs=(16384, 2048) idx=(16384, 4) K_actual=4
```

**结论**：K=4 确认。topk_param=8 被 fused_routing 覆盖。decode 阶段 N_dispatch = batch×32 = 16384。

---

### 实验 3：模型参数确认

**数据**（从 config.json）：
- hidden_size = 2048（不是之前假设的 2560！）
- moe_intermediate_size = 512
- num_experts = 256, num_experts_per_tok = 8
- num_hidden_layers = 20, first_k_dense_replace = 1 → 19 MoE layers

**修正后的 per-expert 指标**：
- weight: 6.29 MB (w13: 4.19 MB + w2: 2.10 MB)
- FLOPs/token: 6.29M

### 实验 4：Kernel Sweep (batch=128→2048)

**设计动机**：测量 f(T) = quant_apply time vs per-expert token count，验证 roofline 转换点。

**命令**：
```bash
torchrun --nproc-per-node=8 bench_bsp_moe_dp2.py --config-set bspg_source --profile-target bsp --batch-size {128,256,512,1024,1280} --component-timing --per-layer-timing --num-runs 1 --no-quality
# batch=2048 需要 tp=2 避免 OOM (prefill logits [1024, ~96, 157184] float32 太大)
torchrun --nproc-per-node=8 bench_bsp_moe_dp2.py --config-set bspg_source --profile-target bsp --batch-size 2048 --tp-size 2 --gen-length 32 --component-timing --num-runs 1 --no-quality
```

**数据**（GS 路径 quant_apply rank-max, 19 层总和）：
| batch | T_avg/expert | AI | quant_apply | scaling | regime |
|-------|-------------|-----|-------------|---------|--------|
| 128 | 64 | 59 | 19.75 ms | — | memory-bound |
| 256 | 128 | 110 | 21.10 ms | 1.07x/2x | memory-bound |
| 512 | 256 | 192 | 26.69 ms | 1.26x/2x | memory-bound |
| 1024 | 512 | 307 | 41.30 ms | 1.55x/2x | ~transition |
| 1280 | 640 | 349 | 51.35 ms | 1.24x/1.25x | near-linear |
| 2048 | 1024 | 439 | 78.80 ms | 1.53x/1.6x | compute-bound |

**结论**：转换点 ~batch=900 (T≈450)，与理论 T=479 (AI=295) 吻合。batch=512 确实 memory-bound。

---

### 实验 5：EPLB 在 Compute-Bound 下 (batch=2048)

**设计动机**：如果 memory-bound 是 EPLB 无效的原因，那 compute-bound 下应该有效。

**命令**：
```bash
torchrun --nproc-per-node=8 bench_bsp_moe_dp2.py --config-set bspg_source --profile-target bsp --batch-size 2048 --tp-size 2 --gen-length 32 --component-timing --num-runs 1 --no-quality --eplb-runtime-enable --eplb-runtime-redundant-experts 32 --eplb-runtime-disable-after-build
```

**数据**：
| | EPLB OFF | EPLB ON | Delta |
|--|----------|---------|-------|
| qa_max | 78.80 ms | 79.68 ms | +0.88 ms |
| qa_spread | 1.26 ms | 7.24 ms | +5.98 ms |
| GS e2e | 199.43 ms | 200.12 ms | +0.69 ms |

Combine 分析：
- combine rank-min: 18.50 → 17.69 ms (-0.81 ms) → 通信没变慢
- combine rank-max: 19.78 → 25.29 ms (+5.51 ms) → 纯等待

**结论**：EPLB 在 compute-bound 下仍无效。它增大了 quant_apply spread（非瓶颈 GPU 变快，瓶颈 GPU 不变），导致更多等待。

---

### 实验 6：Per-Layer Per-GPU Timing

**设计动机**：精确测量单次 forward 中每层每 GPU 的 kernel 时间差异。

**实现**：make_timed_forward_impl 加 layer_id 参数，timer key 改为 "moe.quant_apply.L{i}"。

**数据**（GS 路径）：
- batch=512: per-layer gap 范围 0.02-0.07 ms/layer（L18 例外 0.21 ms）
  - Σ qa_gap = 0.927 ms
  - gap/max = 3.4%
- batch=2048: per-layer gap 范围 0.06-0.28 ms/layer
  - Σ qa_gap = 3.141 ms
  - gap/max = 3.9%

**对比模拟预测**：
- 模拟（用聚合 heatmap）：6.60 ms (batch=512) / 33.06 ms (batch=2048)
- 实测：0.93 ms / 3.14 ms
- 模拟高估 7-10x（聚合数据夸大了 per-forward 不均衡）

---

### 实验 7：因果分析 (Token Count ↔ Kernel Time)

**设计动机**：0.93 ms 的 timing gap 是来自负载不均衡还是硬件噪声？

**实现**：_per_layer_causal_analysis 函数，收集 per-rank per-layer 的 (token_count, qa_time) 配对数据。

**数据**（GS 路径 batch=512, 19层×8GPU=152 点）：
- Mean per-layer Pearson r = +0.928
- Per-layer r 范围：+0.84 ~ +0.996（18/19 层 > 0.84）
- tok_CV = 0.286, qa_CV = 0.017
- Dampening = qa_CV / tok_CV = 0.06x

**结论**：timing gap 确实来自负载不均衡（r=0.93），但 dampening 极强（50% token 差异→仅 3% timing 差异）。

**纠错**：Overall pooled r=0.06 是误导（不同层的绝对值不同，pooling 稀释信号）。正确指标是 per-layer r。

---

### 实验 8：Active Expert Sweep

**设计动机**：验证 kernel 时间是否依赖 pairs 在 experts 间的分布。

**实现**：active-expert-sweep mode，强制 routing 到 N 个 local experts。

**数据**（total_pairs=8192 固定）：
| active_experts | tok/expert | kernel_ms |
|---------------|-----------|-----------|
| 4 | 2048 | 1.145 |
| 16 | 512 | 1.148 |
| 32 | 256 | 1.297 |

**结论**：分布不影响 kernel 时间。kernel_time = f(total_pairs)。

---

### 实验 9：Total Pairs Sweep

**数据**（32 active experts 固定）：
| total_pairs | kernel_ms | ratio vs 8192 |
|------------|-----------|---------------|
| 2048 | 1.102 | 0.96x |
| 4096 | 1.097 | 0.96x |
| 8192 | 1.147 | 1.00x |
| 16384 | 1.287 | 1.12x |
| 32768 | 1.687 | 1.47x |

**结论**：kernel 时间随 total_pairs 亚线性增长。有 ~1.1 ms floor（memory-bound baseline）。

### 实验 10：2D Sweep (pairs × active_experts)

**数据**（kernel_ms per layer, rank-max）：
```
         act=4   act=8   act=16  act=32
p=1024   1.09    1.33    1.09    1.23    spread=0.25ms (23%)
p=2048   1.17    1.26    1.16    1.09    spread=0.17ms (15%)
p=4096   1.10    1.21    1.14    1.10    spread=0.11ms (10%)
p=8192   1.21    1.19    1.14    1.29    spread=0.15ms (13%)
p=16384  1.33    1.28    1.30    1.33    spread=0.05ms (4%)

```

**结论**：低 pairs 时 active experts 有 10-23% 影响（weight loading 可见），高 pairs 时 <6%。Weight loading 不是主要瓶颈。

### 实验 11：Tiling Config 分析

**发现**：
- Config 文件名格式：`E={local_experts},N={intermediate_size},device_name=xxx.json`
- 选择逻辑：`E, _, N = w2_shape` → 按 M (sorted_token_ids size) 索引
- **E=32, E=34, E=36 的 config 与 E=256 100% 相同**
- E=62, E=128, E=512 有独立不同的 config
- 结论：E=32 的 config 是从 E=256 复制的，未独立 auto-tune

## 关键纠错

### 纠错 1：跨层不抵消
- 错误说法：不同层的热点 GPU 不同，累加后互相抵消（"第二重统计平滑"）
- 纠正：每层有 combine barrier 做同步，不存在跨层抵消。每层的不均衡成本独立累加。

### 纠错 2：combine 开销来源
- 错误说法：EPLB 增加了 combine 的通信量（redundant experts 改变数据布局）
- 纠正：combine rank-min 下降（通信没变慢），rank-max 上升（等待增加）。开销 100% 来自等待。

### 纠错 3：模型 hidden_size
- 错误说法：hidden_size=2560（从 per-expert weight=7.9MB 反推）
- 纠正：hidden_size=2048（直接读 config.json），per-expert weight=6.29MB。

## 最终因果链

```
EPLB 在 EP=8 下无效的根因：

1. kernel_time = f(total_pairs_per_GPU)，不依赖分布
   → EPLB 只改分布不改总量 → 原理上无法优化 kernel

2. 统计平滑 (32 experts/GPU) 把 per-GPU tok_CV 压到 0.286

3. Memory-bound dampening (0.06x) 把 28.6% token 不均衡压成 1.7% timing 不均衡

4. 实际 per-forward 不均衡成本仅 0.93 ms (1.2% of 77ms)

5. EPLB redundant experts 反而增大 spread → 净负优化
```

## Tiling Config 发现与下一步

E=32,N=512 的 FusedMoE config 完全复制自 E=256。其他 E 值（62/128/512）有独立 auto-tuned config 且差异显著。

下一步方案（已获用户批准）：
1. 确认实际 EM（sorted_token_ids 大小）
2. 快速对比 E=62/128/512 的 config
3. 384 组合 grid search
4. 端到端验证

搜索空间：BLOCK_SIZE_M={16,32,64,128}, N={32,64,128,256}, K={64,128}, GROUP_SIZE_M={1,16}, warps={4,8}, stages={2,3,4}
