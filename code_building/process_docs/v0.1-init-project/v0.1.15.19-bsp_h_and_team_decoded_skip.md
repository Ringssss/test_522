# v0.1.15.19 BSP-H 探索 + TEAM Decoded-Token Skip 集成

## 主题

BSP-H collective 优化探索（AllReduce 替换 combine+gather）+ TEAM decoded-token skip 组件搬运与 null expert 方案设计

## 动机

上轮 (v0.1.15.18) 完成了 SP-LM Head 优化，累积加速到 58.2 ms/fwd (1.21x)。本轮探索两个方向：(1) BSP-H 优化 MoE combine + TP AllGather 的 collective 效率；(2) TEAM decoded-token skip 减少 MoE 计算量。

## 实验记录

### 实验 1：BSP-H AllReduce 方案（naive）

**方法**：在 bench script 中实现 `make_bsp_h_decoder_forward`，用 EP AllReduce 替换 combine(EP RS) + TP AllGather，融合残差到 AllReduce 中。

**数据** (C12 batch=512, gen=256, 2 runs average)：
- GS: 59.24 ms/fwd
- H: 57.08 ms/fwd → **-2.17 ms (-3.7%)**

**Component timing 分析**：
- AllReduce (11.17 ms) vs combine+gather (11.67 ms) → 仅省 0.5 ms
- 主要收益来自消除 attention input TP AllGather (~2.5 ms)
- 但 BSP-H 的 attention RS 是 bench script 版（2.6 ms），G 的是源码版（5.1 ms），不完全可比

**结论**：AllReduce 替换在 NVLink 8-GPU 配置下收益有限。更重要的发现是，BSP-H 改变了层间 layout（输出 [N_dp,h] 而非 SPHiddenState），丢失了 SP 间的 norm 计算节省。

### 实验 2：BSP-H 概念重审

**用户指正**：原始 BSP-H 定义是 "hierarchical collective: EP reduce_scatterv + TP gather 的融合或重排"，不是简单的 AllReduce 替换。

**分析**：
- TP attention 要求所有 GPU 处理相同 token（RowParallelLinear 语义），无法通过改变并行策略消除 TP AllGather
- Token-parallel attention（full heads per GPU）理论上省 7.5 ms，但大模型不泛用（需要全量 attention 权重）
- 真正的 SP 优化空间在 MoE 路径：dLLM 的 decoded token skip

### 实验 3：TEAM 组件分析与搬运方案

**TEAM 核心思想**：dLLM block diffusion 中，已 decoded 的 token 的 MoE 计算结果不影响最终输出（threshold decoder 只看 MASK 位置），可用缓存替代。

**TEAM 安全性分析**：
- 缓存在 decoded 那一刻冻结，后续不更新（非"滚动更新"）
- decoded 位置变化小（cosine sim 0.97-0.99）
- 误差通过 attention 间接传播是二阶效应
- threshold 提供容错（小误差不翻转决策）
- TEAM 不跳过 MASK 位置 MoE（vs 我们之前失败的 Stable Cache 跳过了 MASK）

### 实验 4：TEAM v1 Extract+Pad 方案

**方法**：提取 MASK-only tokens → pad to max_n_mask → nested set_forward_context → dispatch+kernel+combine on MASK subset → merge with cache。

**数据** (C12 batch=512, no-quality)：
- G: 59.42 ms/fwd
- TEAM v1: 68.84 ms/fwd → **退化 9.4 ms**
- skip_ratio: 55.1%, path counts 一致

**退化根因**：
- Per-layer AllReduce × 2 (max_n_mask + DPMetadata): ~3.4 ms
- Padding to max_n_mask 浪费: ~2-3 ms
- Cache clone + merge: ~0.5 ms
- MoE kernel 非线性缩放: ~2-3 ms

**Component timing**：native_forward 从 39.7 → 33.5 ms（-6.2 ms），但 overhead 吃掉全部收益。

### 实验 5：TEAM Null Expert 方案

**核心设计**：扩展 expert_map 加一个 "null expert"（id=256, map=-1），让 decoded tokens 的 routing 指向它。FusedMoE kernel 天然跳过 expert_map=-1 的 pairs。零 Python overhead。

**验证**：
- `moe_align_block_size(topk_ids with 256, num_experts=257)` 正确处理 ✓
- `fused_experts` 对 null expert tokens 输出精确零 ✓
- mask 对齐逻辑正确 ✓

**数据** (C12 batch=512, no-quality)：
- G: 58.92 ms/fwd
- TEAM null: 71.20 ms/fwd → **退化 12.3 ms**

**Component timing 分析**：
| 组件 | G (ms) | TEAM null (ms) | 差异 |
|------|--------|---------------|------|
| dispatch | 11.1 | 8.2 | -2.9 |
| quant_apply (kernel) | 20.0 | **20.9** | **+0.9** |
| combine | 9.2 | 8.4 | -0.8 |
| cache_merge | — | **2.5** | +2.5 |
| tp_all_gather | 2.9 | 4.1 | +1.2 |

**kernel 没有加速的原因**：
- Decoded tokens → expert 256 → 560 extra grid blocks（虽然 skip 但有调度开销）
- Memory-bound kernel：32 local experts 的 weight loading 不变
- dispatch/combine 仍搬运全量 tokens（未减少通信）

### 实验 6：质量验证

**cache-only（无 null expert）**：质量可接受——"one by step" vs "step by step"，TEAM 固有近似误差。

**null expert + `go[dec]=-1e9`**：质量完全崩坏——乱码输出。根因：-1e9 破坏 EB hot_update 的 pop 统计。

**null expert 不改 logits**：质量仍然崩坏。**根因仍在调查中。**

**当前状态**：null expert kernel 机制验证通过（精确零），mask 对齐验证通过，但完整流程中质量崩坏。待 debug。

## 关键未解决问题

### Null Expert 质量崩坏根因

已排除：
- kernel 输出不为零 → 排除（独立测试确认精确零）
- mask 对齐错误 → 排除（验证通过）
- EB logits 修改 → 排除（去掉 -1e9 后仍崩坏）

仍在怀疑：
1. `idx[dec]=256` 的 in-place 修改是否影响 fused_moe 内部的某个中间状态
2. expert_map 从 [256] 扩展到 [257] 是否影响 _timed_fwd_impl 的某个隐式假设
3. routing wrapper 的返回 tensor 是否和下游有 aliasing 关系
4. combine ReduceScatterV 是否对 expert 256 的 pairs 有非零副作用

### 建议的下一步 debug 方向

2. 对比 null expert 和 cache-only 在 layer 0 的 y_sp 差异

4. 尝试不用 _timed_fwd_impl（直接用原始 forward_impl + tuple 处理）看是否修复
