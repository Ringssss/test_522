## 2. DeepEP V1 HT 质量修复

### Bug
`bench_multi_gpu_dp.py` 设置 `VLLM_ALL2ALL_BACKEND=deepep_high_throughput` 后，vllm 的 `DeepEPHTAll2AllManager` 被正确创建，但 `FusedMoEModularKernel`（含 `DeepEPHTPrepareAndFinalize`）未被初始化。

原因：dInfer 的 standalone pipeline 不调用 `prepare_communication_buffer_for_model(model)`，这是 vllm worker 在模型初始化后执行的。该函数遍历所有 FusedMoE 层，调用 `quant_method.init_prepare_finalize(layer)` 创建 modular kernel。

### 修复
```python
from vllm.distributed import prepare_communication_buffer_for_model
prepare_communication_buffer_for_model(model)
```

### 验证
- 修复前：4卡输出全空（0/5 FAIL），forward 次数 152（不收敛）
- 修复后：4卡质量 5/5 PASS，forward 次数 284（和 naive 一致）
- 逐层 norm 精确匹配 naive

## 3. DeepEP V2 ElasticBuffer

### 成果
- 2 卡初始化成功，逐层 norm 完全匹配
- V2 为 EP=4 计算 num_sms=16（vs V1 的 20）

### 阻塞
- 4 卡需要 NCCL GIN → 需要 IMEX daemon → 驱动 580.65 不支持 GIN
- EP_DISABLE_GIN=1 可跳过 GIN assert，但 4 卡 generate 循环崩溃（CUDA launch failure）
- 单次 forward 正确但多次 forward 不稳定 → V2 非 GIN 回退路径不完善

### 结论
V2 在驱动 580.65 上 4 卡不可用。需升级驱动到 580.126+ 才能使用 GIN。

## 4. AllReduce vs AllToAll 分析

AllReduce 快 22%（11.59 vs 14.80）的根本原因：
- AllReduce 每层 1 次通信 (~1ms)，AllToAll 每层 2 次 (~2ms)
- NCCL AllReduce 零 SM 开销，DeepEP V1 占 20 SMs
- AllToAll 省的 attention 计算 (~7.5ms) 无法弥补多出的通信 (~19ms)

## 5. Attention TP 方向（★★★ 下一步核心）

当前 dInfer 的 attention 不做 TP（tp_size=1 硬编码，nn.Linear），导致 AllReduce EP 下 attention 4x 冗余。

vllm 标准 MoE 部署：tp=N + ep=N（同组 GPU），attention TP 分 heads + MoE EP 分 experts。

目标：改造 LLaDA2MoeAttention 支持 TP
- Q/K/V: nn.Linear → QKVParallelLinear / ColumnParallelLinear
- O: nn.Linear → RowParallelLinear（自带 AllReduce）
- 去掉 tp_size=1 硬编码
- 预期 tp=4+ep=4 配置下 ~34 ms/fwd（vs 当前 41.24）
