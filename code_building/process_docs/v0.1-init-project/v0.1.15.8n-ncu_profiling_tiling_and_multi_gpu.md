```
fused_experts_impl():
```

### S_mask 效果验证
- GEMM-1 avg read 740.6 MB → ~177 experts（理论 S_mask avg=165.6，多出部分为 activation）
- GEMM-2 avg read 342.5 MB → ~163 experts（和理论完全吻合）

### GEMM-2 效率低的根因
- K=512 → K-loop 只有 8 次迭代（vs GEMM-1 的 32 次）
- 4-stage pipeline 在 8 次迭代中 startup/drain 占 50%
- Pipeline 效率：GEMM-1 87.5% vs GEMM-2 62.5%

### 真实有效带宽
- ncu bytes (2182 GB) / CUDA Event time (1362ms) = 1602 GB/s (47.8%)
- 这是 fused_experts 整体（含 silu+reduce+align）的利用率
- 纯 GEMM kernel 内部：2079 GB/s (62.1%)

## 9. 8-GPU Expert Parallelism 验证（★ 首次跑通）

### 硬件
8× H100 80GB HBM3, NV18 NVSwitch 全互联 (~900 GB/s)

### 结果

| Config | GPUs | Time(s) | Fwd | ms/fwd | vs 1-GPU |
|--------|------|---------|-----|--------|----------|
| C5 | 1 | 12.42 | 278 | 44.69 | — |
| C5 | 8 | 11.14 | 282 | 39.49 | -11.6% |
| C10-M5 | 1 | 12.02 | 280 | 42.91 | — |
| C10-M5 | 8 | 11.43 | 283 | 40.38 | -5.9% |

### 发现
1. EP 确实生效：每卡 32 local experts，GPU memory 5.9GB（vs 单卡 ~15GB）
2. 加速比低（11.6%）：AllReduce 通信 + 非 MoE 组件未被加速（Attention 29.4%）
3. E=32 没有 auto-tuned config → 回退到 default config → 性能受损
4. C10-M5 在 8 卡下反而比 C5 慢：EB 开销在 EP 场景下 ROI 降低
5. 质量验证通过：8-GPU 输出和单卡一致

### EP 通信架构分析
- 当前走的是 AllReduce EP（dInfer 的实现方式）
- vllm 标准 EP 用 AllToAll（需要 dp_size > 1，通过 pplx/deepep kernel）
- AllReduce 通信量小（66MB/层）但有零写 block 开销
- AllToAll 通信量大（~946MB/层）但零冗余计算
- 对我们的 case（H=2048 小），AllReduce 反而更优

### EB 多卡兼容性确认
- EB 不需要多卡协调：gate logits 在每卡一致 → S_mask 自然相同
- BlockDiffusionLLM 不需要多卡设计：多卡通信在 model.forward() 内部处理

## 12. ncu 深度诊断（★★★ 本轮新增 — 2026-04-22）

### 12a. 诊断方案

三轮 ncu 深度采集，每轮 38 launches（1 steady-state forward），skip 前 38 launches（cold start）：
1. 第三轮：coalescing (sector/request) + bank conflicts + warp stall（`--metrics` 模式）
2. 第四轮：SchedulerStats + WarpStateStats sections
3. 第五轮：`smsp__warps_issue_stalled_*.avg` raw counters（完整 stall 分项）

注意：`smsp__average_warp_latency_issue_stalled_*.pct` 在 Triton JIT kernel 下全部返回 0，需要使用 `smsp__warps_issue_stalled_*.avg`（raw counter .avg）才能获取有效数据。

### 12b. 结果

#### Bank Conflicts: **零**
GEMM-1 和 GEMM-2 的 shared memory load/store bank conflicts 均为 0。Triton swizzle 完美。

#### Coalescing: **正常**（非瓶颈）
| Kernel | sectors/request | 解释 |
|--------|----------------|------|
| GEMM-1 | 15.08 | vec-8 bf16 loads (16B/thread → 16 sec/req ideal) |
| GEMM-2 | 12.67 | mixed vec widths (activation narrower) |

15 sec/req 看似 "poor"，但对于 Triton 的 vectorized bf16 loads 这是正常的（每线程 ~8 个 bf16 元素）。

#### Warp Stall Breakdown（★★★ 关键发现）

| Stall Reason | GEMM-1 | GEMM-2 | 含义 |
|---|---|---|---|
| **long_scoreboard** | **25.7%** | **27.7%** | 等 HBM 数据 |
| **barrier** | **24.4%** | **12.9%** | CTA barrier 同步 |
| **wait** | **13.6%** | **16.4%** | Pipeline barrier/sync |
| selected (productive) | 12.5% | 14.1% | 真正在执行指令 |
| not_selected | 5.0% | 5.5% | 就绪但未被调度 |
| math_pipe_throttle | 5.0% | 4.6% | 计算管线满 |
| mio_throttle | 4.6% | 4.8% | MIO 队列满 |
| dispatch_stall | 4.6% | 3.7% | 分发停滞 |
| short_scoreboard | 2.4% | 6.1% | MIO/smem 等待 |

#### Scheduler Statistics

| Metric | GEMM-1 | GEMM-2 |
|--------|--------|--------|
| No Eligible warps | 74.9% | 71.9% |
| Active warps/scheduler | 2.00 | 1.99 |
| Eligible warps/scheduler | 0.35 | 0.39 |
| Warp cycles per issued inst | 7.96 | 7.10 |

### 12c. 30% BW Gap 根因分解

```
100% HBM Peak BW (3.35 TB/s)
 │
 ├── ~38% BW gap 来源:
 │   ├── [~18%] Pipeline sync: barrier(24%) + wait(14%) = 38% stall cycles
 │   ├── [~12%] HBM latency hiding 不足: long_scoreboard 26%, Occ=12.5%
 │   ├── [~5%]  Dispatch + throttle overhead
 │   └── [~3%]  GEMM-2 pipeline bubble: K=512 → 8 iter, eff 62.5%
 │
 └── ~62% 有效利用 (2079 GB/s)
```

**结论：BW gap 不是来自访存效率问题（coalescing 好、bank conflict 零），而是来自 pipeline 同步和 latency hiding 不足。fused_moe_kernel 内部已接近 vllm auto-tuned 的最优点。**

## 13. Routing TopK 压缩实验（★★★ 本轮新增）

### 13a. 设计

Expert Budgeting 的第二维度：S_mask 缩小候选池（D1），topk 缩小选中数（D2）。

- S_mask 仍用 K=8 计算（controller 的 K 不变）
- 只在 fused_routing() 调用时 override K=4, tkg=4
- 即"候选池不缩小，每 token 选中数减半"
