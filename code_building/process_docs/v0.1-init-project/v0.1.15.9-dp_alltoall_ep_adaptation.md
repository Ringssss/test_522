# v0.1.15.9 — dLLM DP + AllToAll EP 适配（Phase 1: Naive 后端）

## 归档时间：2026-04-24
## 阶段：v0.1-init-project / v0.1.15.9

## 1. 本轮概述

将 dInfer 的多卡 MoE 推理从 AllReduce EP (dp=1, tp=N) 升级到 DP + AllToAll EP (dp=N, tp=1)。
这是全新的工程方向——dLLM block diffusion 迭代式推理 + AllToAll EP 的组合，目前 vllm 和 sglang 都没有实现过。

## 2. 核心技术背景

### AllReduce EP vs AllToAll EP

| 维度 | AllReduce EP (旧) | DP AllToAll EP (新) |
|------|-------------------|---------------------|
| 配置 | tp=N, dp=1, ep=N | tp=1, dp=N, ep=N |
| 每卡输入 | 相同 128 prompts | 不同 128/N prompts |
| Attention | 冗余（N卡算相同数据）| 无冗余（各卡算不同数据）|
| MoE 通信 | AllReduce | AllToAll dispatch/combine |
| MoE 零写 | 有（expert_map=-1 写零）| 无（dispatch 后只有 routed token）|
| KV Cache | N 份冗余 | 1/N 无冗余 |

### dInfer 的 TP 不分片 Attention

关键发现：dInfer 的 `LLaDA2MoeAttention` 使用原生 `nn.Linear`（非 vllm 的 ColumnParallelLinear），
`self.tp_size = 1` 硬编码。所以 tp=4 时 attention 权重在每卡完整复制，4 卡对相同 128 prompts 算完全相同的 attention = 3/4 纯冗余。
代码位置：`modeling_llada2_moe.py` line 756-767。

### dLLM + AllToAll EP 的独特挑战

AR 推理每步恰好 1 次 forward，调度器保证对齐。dLLM 的 block diffusion 有 3 层嵌套循环，
每层的 forward 次数由数据（token 置信度）决定，不同 DP rank 处理不同数据 → forward 次数天然不对齐 → AllToAll collective 死锁。

这是一个 **全新问题**——vllm 没有 dLLM，sglang 的 dLLM 不支持 AllToAll EP（两者互斥）。

## 3. 修改的文件和改动

### 文件 1: modeling_llada2_moe.py
- **_maybe_patch_all_reduce()**: 条件化 monkey-patch，只在 tp>1 时才替换 tensor_model_parallel_all_reduce
- **_get_ep_rank_and_size()**: 优先用 EP group rank/size 做 expert 分片
- **_moe_forward_with_context()**: 在 MoE 层注入 ForwardContext (DPMetadata)
- **load_state_dict()**: 两处 ep_rank/ep_size 改用 _get_ep_rank_and_size()

### 文件 2: modeling_fused_olmoe.py
- **去掉无条件 patch** (line 51): `vllm_distributed.tensor_model_parallel_all_reduce = torch_all_reduce` → 注释掉
- ★★★ 这是质量 bug 的根因：模块加载时无条件用 world group all_reduce 替换 TP group all_reduce，
  导致 combine 后的正确结果被再次 all_reduce → 输出膨胀 dp_size 倍

### 文件 3: generate_uniform.py
- **BlockDiffusionIteration.forward()**: 去掉了之前添加的 _model_call wrapper（ForwardContext 改在 MoE 层注入）
- **BlockDiffusionRunner.decode()**: 3 个改动：
  - DP 模式检测（从 vllm_config 读 dp_size）
  - 停止条件全局同步：`while True` + `all_reduce(MAX)` 替代本地 `while (mask).sum() > 0`
  - unroll=1 强制（DP 模式下 `unroll_k=1`，防止不同 rank forward 次数不对齐）
  - 禁用 mid-block batch shrinking（DP 模式下跳过 select_undecoded 的 batch 缩减）
- **naive_batching_generate()**: early_stop 全局同步（`all_reduce(MIN)` 在 DP group 上）

### 文件 4: parallel_strategy.py
- **broadcast_if_needed()**: 默认使用 TP group（tp=1 时 no-op），防止 DP 模式下覆盖其他卡数据

### 文件 5: bench_multi_gpu_dp.py（新建）
- 两阶段分布式初始化：先 dp=1 init（跳过 vllm DP 端口调整），再 dp=N initialize_model_parallel
- Input 分片 + Output 聚合
- C5 fused routing 测试

## 4. 解决的技术问题

### 问题 1: vllm init_distributed_environment 的 DP 端口调整
vllm 在 dp>1 时重新计算 rank 和 rendezvous 端口，导致 torchrun 的进程无法连接。
解决：两阶段初始化——先 dp=1 初始化 torch.distributed，再 dp=N 创建 DP/EP groups。

### 问题 2: ForwardContext 缺失
NaiveAll2AllManager.dispatch() 需要 ForwardContext.dp_metadata。dInfer 的 generate loop 不设 ForwardContext。
解决：在 _moe_forward_with_context() 中注入（覆盖 prefill 和 decode 两个阶段）。

### 问题 3: dLLM 三层 forward 对齐
| 层级 | 描述 | 解决方式 |
|------|------|---------|
| Block 内 while | 不同 rank 收敛速度不同 | unroll=1 + all_reduce(MAX) |
| Block 间 for | 不同 rank early_stop 不同 | all_reduce(MIN) on DP group |
| Prefill | Pad 到相同长度 → 自然一致 | 无需额外处理 |

### 问题 4: 输出质量乱码（★★★ 最关键的 bug）
根因：`modeling_fused_olmoe.py` line 51 在模块加载时**无条件**将 tensor_model_parallel_all_reduce 替换为 world group all_reduce。
链路：combine (DP group all_reduce) 正确聚合 → maybe_all_reduce_tensor_model_parallel (被 patch 成 world group all_reduce) 再次聚合 → 输出 × dp_size。
诊断方法：逐层 hidden_states norm 对比，发现 L1 开始 norm 膨胀恰好 4 倍 = dp_size。
修复：注释掉 olmoe 的无条件 patch。

### 问题 5: GPU 0 被占用导致 NCCL init hang
NCCL init_process_group 在 NVLink 全互联节点上会探测所有 GPU 的 P2P 连接。其他用户占用 GPU 0 会阻塞。
这不是代码问题，是系统环境限制。解决：让其他用户设置 CUDA_VISIBLE_DEVICES。

## 5. 性能结果

### 4 卡完整对比（batch=128, gen=256, HetEval-128）

| Config | Time(s) | Fwd | ms/fwd | vs 1-GPU | 质量 | 内存/卡 |
|--------|---------|-----|--------|----------|------|---------|
| C5 1-GPU | 12.42 | 278 | 44.69 | — | 5/5 | ~15GB |
| C5 AllReduce 4-GPU | 11.59 | 281 | 41.24 | -7.7% | 5/5 | ~15GB |
| C5 DP AllToAll 4-GPU | 15.72 | 283 | 55.55 | +24.3% | 5/5 | 9.7GB |

### Naive AllToAll 比 AllReduce 慢的原因
1. NaiveAll2AllManager 用 broadcast × dp_size + all_reduce，通信效率极低
2. dispatch 后 MoE 计算量不减（每卡处理 gathered 128 prompts）
3. Attention 减少 75% 的收益被通信开销完全抵消

### 收益在哪
- 内存：9.7GB vs 15GB（-35%），可以跑更大 batch 或更大模型
- 框架正确性已验证，可直接升级 DeepEP/pplx 后端
