# v0.1.15.21 — TEAM Sparse Kernel 多路径探索（TV4/TV5/TV4m）

## 主题

在 TD4（null expert + cache）基础上，探索更优的 decoded-token skip 实现路径，消除 CPU launch overhead，逼近 G 性能。

## 动机

上轮 (v0.1.15.20) 完成了 TD4 的质量排查和 cache 状态机设计。TD4 质量接近 G 但性能慢 24%（73.79 vs 59.42 ms/fwd），主要开销来自 null expert kernel penalty (+4.2ms)、routing wrapper (+4.1ms)、cache merge (+2.5ms)。本轮目标：找到性能更优的实现路径。

## 实验记录

### 实验 1: TD4 Cache Write 修复

**设计动机**：发现 cache write/read 逻辑与设计文档不一致——刷新步不写 cache，跳过步写 cache（应反过来）。

**实现**：
- 刷新步（null_sp=None）：写 cache（y.detach().clone()）
- 跳过步（null_sp!=None）：只读 cache merge，不写

**数据**：
| Config | 修复前 | 修复后 | Δ |
|--------|-------|--------|---|
| TD4 | 73.43 | 73.20 | -0.23 ms |

Cache write 从 0.69 ms/fwd 降到 0.05 ms/fwd，但总改善仅 ~0.5ms（cache write 本来就不是主要开销）。

**结论**：cache write 逻辑已修正。真正的开销是 null expert kernel (+4.2ms) 和 routing wrapper (+4.1ms)。

---

### 实验 2: 删除 `.any()` 冗余检查

**实现**：cache merge 中 `if null_sp.any() and ...` 的 `.any()` 是冗余的（进入分支时必然有 null 位置）。

**数据**：TD4 从 73.20 降到 72.93 ms/fwd（-0.27ms）。

---

### 实验 3: TD8 无 Cache（质量验证实验）

**设计动机**：验证 cache merge 是否必要。

**数据**：TD8 质量严重崩坏（#8/#13/#19/#28 大量重复/循环文本），确认 cache 对质量是必要的。

---

### 实验 4: TV4 Sparse Kernel 原版

**设计动机**：不用 null expert，直接 extract compute tokens → compact kernel → scatter back。

**实现**：
- model_forward: AllGather null mask → compute_indices（一次/forward）
- forward_impl: dispatch(FULL) → routing(FULL) → extract(3×index_select) → fused_experts(COMPACT, 256 experts) → scatter(index_copy_) → combine(FULL) → cache merge

**数据**：TV4 原版 65.69 ms/fwd (+11.3% vs G)

---

### 实验 5: TV4 Buffer 优化

**实现**：预分配 buf_hs/buf_ids/buf_wts/buf_out_g/buf_cached，用 index_select(out=) 替代 fancy indexing，消除 per-layer torch.zeros。

**数据**：
| Config | 平均 ms/fwd | vs G |
|--------|------------|------|
| G | 59.03 | — |
| TV4 buffer opt | 59.49 | +1.2% |

**结论**：从 +11.3% 压缩到 +1.2%，主要通过消除 cub trio（boolean indexing）和 tensor 分配。

---

### 实验 6: nsys 三方对比（G vs TV4 opt vs TV5）

**数据**：
```
              launches      kernel_time
G:           4,656,532      216,682 ms
TV4 opt:     5,075,036      206,983 ms (kernel 少 9.7s，但 launches 多 418k)
TV5:         4,948,316      220,243 ms (kernel 多 3.6s，launches 多 292k)
```

**关键发现**：
- TV4 kernel time 比 G 少 9.7 秒但端到端反而慢——因为 +418k launches × 6.6μs/launch 的 CPU overhead
- cudaLaunchKernel CPU 时间：G 21.5s, TV4 23.8s (+2.3s)
- GPU 空泡 = kernel 节省 + e2e 退化 = 9.7 + 0.34 = 10 秒

---

### 实验 7: TV5 topk_ids Skip

**关键发现**：vllm `moe_align_block_size` C++ kernel（`moe_align_sum_kernels.cu` line 126）：
```cpp
if (expert_id >= num_experts) { continue; }
```
同样 `count_and_sort_expert_tokens_kernel` line 303 也有此保护。

**实现**：routing 后设 `topk_ids.index_fill_(0, null_indices_gathered, num_experts)` → 两个 C++ kernel 自动跳过 null tokens → sorted_token_ids 不含 null → fused_moe_kernel 不处理。然后 `c_out.index_fill_(0, null_indices_gathered, 0)` 清零 null 位置（避免 garbage 进 combine）。

**数据**：
| Config | 平均 ms/fwd | vs G |
|--------|------------|------|
| G | 59.32 | — |
| TV5 | 59.71 | +0.66% |

**质量**：#0/#13 正确，#19/#28 轻微差异（与 TD4 质量水平一致），path counts 完全一致。

---

### 实验 8: CUDA Event Kernel Phase 实验

**设计动机**：量化"如果消除 CPU launch 空泡，TV4 能比 G 快多少"。

**方法**：在 dispatch 之后、combine 之前插入 CUDA Event 对，测量 kernel phase GPU wall-clock。

**数据**：
```
G kernel phase:   mean 1.067 ms/layer (纯计算，无空泡)
TV4 kernel phase: mean 0.642 ms/layer (含空泡，比 G 快 40%)
```

**结论**：TV4 kernel phase 已比 G 快 40%。理论 native 集成后可达 ~51 ms/fwd (-16% vs G)。

---

### 实验 9: Triton Gather Kernel

**实现**：自定义 `_triton_gather_rows`/`_triton_scatter_rows` 替代 PyTorch index_select。

**数据**：TV4+Triton = 62.57 ms/fwd (+6.3%) — 比 index_select 版慢。

**原因**：每行一个 Triton program，效率低于 PyTorch 的 vectorized_gather（多 launch 但每个 launch 更高效）。

---

### 实验 10: shuffle_rows (vllm C++ kernel)

**发现**：`torch.ops._moe_C.shuffle_rows(input, dst2src_map, output)` 可用，单 kernel gather。

**数据**：TV4+shuffle_rows = 60.65 ms/fwd (+2.3%) — 比 index_select 略慢（需 int32 cast）。

---

### 实验 11: TV4m Mapped Kernel（未完成）

**设计动机**：融合 gather + fused_moe + silu/moe_sum（compact cache）。

**实现**：自定义 `_fused_moe_kernel_mapped` Triton kernel，加 `input_map_ptr` 参数。第一个 GEMM 从 FULL A 读（via input_map），写入 compact intermediate_cache。silu/moe_sum 在 compact 上操作。

**状态**：crash（illegal memory access），原因是 sorted_token_ids 的 padding sentinel 值越界 input_map。需要在 input_map load 时增加更严格的 mask 保护。

## 关键认知

### moe_align_block_size 的 skip 机制

vllm C++ kernel `moe_align_sum_kernels.cu` 中，两个关键位置有 `expert_id >= num_experts → continue` 保护。这意味着不需要创建 expert 257——只需设 topk_ids 为 >= 256 的值，kernel 就自动跳过。

### CPU Launch Overhead 是 Monkey-Patch 的硬瓶颈

nsys + CUDA API timing 证明：
- G: 3.19M launches, 21.5s CPU on launches
- TV4: 3.61M launches, 23.8s CPU on launches
- 多出的 415k launches × 6.6μs = 2.7s CPU overhead
- 这完全吃掉了 TV4 节省的 10s GPU kernel time

### fused_moe_kernel 的间接寻址

kernel 已通过 `sorted_token_ids` 间接寻址读 A：`a_ptr + offs_token // top_k * stride_am`。TV4m 的 input_map 只是在此基础上多一层间接：先从 input_map 查出真实的 FULL row index，再读 A。

### TV5 是当前最优 Monkey-Patch 方案

+0.66% vs G，代码最简洁（只加 2 个 index_fill_ per layer + cache merge），不需要 gate wrap/routing wrap/expert_map 修改。
