# v0.1.15.12m - M1/M2/M3 BSP-DelayGather 与 EB 三路径实验

## 目标

按照前面讨论的保守主线推进：

- M1：继续使用 BSP/SP MoE，把 TP 内 MoE 侧 token 冗余降下来。
- M2：保守 delayed gather，把 SP layout 保到 MoE 后 residual/norm 末端，在 attention 边界前恢复 full layout。
- M3：不改 EB 算法，只验证三路径通信接口：cold 继续全局保守路径，hot_skip 复用 `s_mask` 零通信，hot_update 做 expert-wise `pop[E]` 合并。

本轮仍然保持 Scheme3 禁止进入 M1/M2/M3 主线。

## 代码改动

- 修改 `codex_coding/src/bench_bsp_moe_dp2.py`。
- 已有 A/B/C 路径基础上补齐 D 路径：
  - `A) C12-AgRs baseline`
  - `B) C12-BSP-MoE`
  - `C) C12-BSP-DelayGather`
  - `D) C12-BSP-DelayGather-M3EPReduce`
- M3 hot_update 改为显式使用 vLLM EP group：
  - `dist.all_reduce(pop, op=SUM, group=get_ep_group().device_group)`
- 增加 controller 全 rank 诊断：
  - 检查 `path_counts` 是否所有 rank 一致。
  - 输出 D 路径 `ep_reduce_calls` / `ep_reduce_mb` 的 min/max。

## 失败与修复

第一次 D-path smoke 出现 rank0 退出、其余 7 个 rank 挂在 GPU1-7 的状态。判断为无效 distributed collective 状态，不纳入结果。

处理：

- kill 掉 orphan rank。
- 将 M3 hot_update 从默认进程组改成显式 vLLM EP group。
- 后续所有 A/B/C/D smoke 与 C12 run 均通过，且 `path_counts` 在 8 rank 上一致。

## 当前结论

- M1/M2 在实验脚本层已经兑现了小幅但稳定的收益：C12 no-timing `76.04 -> 74.35 ms/fwd`，约 `1.023x`。
- M2 的保守 delayed gather 是当前主线里最值得继续下沉的部分。
- M3 的三路径接口可行性已验证：cold/hot_skip/hot_update path counts 一致，hot_update 的 expert-wise `pop[E]` EP all-reduce 可运行。
- 但 M3 不能停留在当前 routing hook 层。如果 routing 仍然发生在 FusedMoE dispatch 之后，M3 只新增 `pop[E]` 同步，不会减少 hidden/router logits 的 AgRs token-level 通信。

## 后续建议

下一步如果继续建设，应优先把 C 路径从实验脚本下沉到 dInfer/vLLM 源码 feature flag，并明确边界：

- attention 输入保持 full layout。
- MoE 前 chunk 到 SP。
- MoE、residual add、post-MoE 局部操作尽量保持 SP。
- attention 前统一 gather。

M3 暂时保留为接口验证结果，不作为首个源码下沉目标。要让 M3 真正兑现收益，需要更深地移动 EB `pop` combine 的位置，使它发生在 token-level AgRs gather 之前，并避免重复做全量 router logits 通信。
