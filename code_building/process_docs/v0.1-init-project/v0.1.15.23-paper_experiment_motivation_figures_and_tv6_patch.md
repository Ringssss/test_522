# v0.1.15.23 — 论文实验：动机图数据采集 + TV6 Patch 独立模块 + 质量/性能验证

## 主题

从优化主线切入论文实验主线：(1) 设计并采集 EB/decoded-skip 动机图所需数据，(2) 将 TV6 优化提取为独立可复用的 patch 模块，(3) 在 bench 框架下进行性能和质量 A/B 验证。

## 动机

上轮 (v0.1.15.22) 完成了 TV4m crash 修复和 TV6 compact dispatch 的完整实现。TV6 确定为优化主线（GPU kernel 端节省 -28.2s，是 TV4m 的 2.2 倍）。本轮切换到论文实验准备：需要可视化数据支撑 EB 和 decoded-skip 机制的合理性，同时需要将 TV6 从 bench 脚本中解耦为独立模块用于标准化实验。

论文动机图的核心叙事：
1. Expert routing 在 block diffusion 迭代中高度稳定且集中 → 支撑 EB 机制
2. Decoded token 的 MoE output 几乎不变（可缓存），MASK token 变化大（需重算）→ 支撑 decoded-skip
3. Cache 随时间漂移，需要周期性刷新 → 支撑 refresh interval M=5

## 实验 1: Expert Routing Stability 数据采集 (Fig.3 Panel a+b)

### 设计动机

展示 dLLM 中 expert routing 的两个关键属性：
- **时间稳定性**：block 内相邻迭代的 active expert set 是否一致（Jaccard similarity）
- **空间集中性**：是否只有少数 expert 承担大部分 routing（CDF / Pareto curve）

这两个属性共同支撑 EB 的核心假设："只需在 block 起始计算一次 expert 预算，后续复用即可"。

### 设计讨论过程

与用户讨论了多种可视化方案：
- **方案 A: Expert 激活位图**（X=expert ID, Y=layer, binary active/inactive）→ 直观但 256 列太宽
- **方案 B: 水平堆叠 bar**（active vs inactive expert count per layer）→ 强调压缩比但丢失分布信息
- **方案 C: Heatmap + CDF 组合**（最终选择）→ heatmap 展示时间稳定性，CDF 展示空间集中性

最终确定：
- Panel (a): 3 个 Jaccard pairwise heatmap（L4/L10/L18，浅/中/深层代表）
- Panel (b): Expert routing concentration CDF（3 条线 L4/L10/L18）

关键约束：**K=8 native routing，无 EB**。这是纯粹的模型行为观测，不能在动机阶段引入我们的解决方案。

### 实现

脚本：`codex_coding/src/collect_routing_stability.py`

**Hook 策略**：wrap 每个 `LLaDA2MoeGate` instance 的 `routing` 方法（instance attribute override）。`static_routing_function(gate, ...)` 调用 `gate.routing(...)`，所以 instance attribute override 能拦截。

**数据收集器 `RoutingCollector`**：
- `on_block_init(block_id)` → 重置 per-block 状态
- `on_forward_start()` / `on_forward_end()` → 追踪每步
- `record(layer_id, topk_ids_cpu)` → 计算 `frozenset(topk_ids.flatten())` 和 `torch.bincount` histogram
- 只收集 TARGET_LAYERS = [4, 10, 18]，节省内存
- Prefill forward 通过 `_current_block_id < 0` guard 自动跳过

**跨 rank 聚合**：`dist.all_gather_object` 收集每个 rank 的 per-layer 数据，rank 0 合并（union active sets, sum histograms）。

**后处理**：
- Jaccard matrix：per-block 计算后截断到 T_min（最短 block 的迭代数），跨 block 平均
- CDF：aggregate histogram across all iterations/blocks → sort descending → cumsum → normalize to 100%

### 命令

```bash
torchrun --nproc_per_node=8 codex_coding/src/collect_routing_stability.py \
    --batch-size 32 --gen-length 256 --block-length 32
```

### 数据

运行信息：268 forwards, 14.2s, 9 blocks per layer, 267 iter records per layer

| Layer | Mean Jaccard | T_min | n_blocks | Active experts (mean) | Top-K cover 50% | Top-K cover 90% |
|-------|-------------|-------|----------|----------------------|----------------|----------------|
| 4 | 0.9489 | 28 | 9 | 234-239 / 256 | Top-38 (15%) | Top-152 (59%) |
| 10 | 0.9499 | 28 | 9 | 230-240 / 256 | Top-46 (18%) | Top-152 (59%) |
| 18 | 0.9483 | 28 | 9 | 210-222 / 256 | Top-32 (13%) | Top-131 (51%) |

输出：`codex_coding/results/plt/routing_stability_data.json` (105.1 KB)

### 结论

- Expert routing 在 block 内跨迭代高度稳定（Jaccard > 0.94）
- Expert routing 高度集中（top 31-51% experts 覆盖 90% routing）
- Layer 18（深层）比 Layer 4（浅层）更集中（top 51% vs 59% cover 90%）
- Active expert 数随层深度递减（L4: 234-239, L18: 210-222），深层更稀疏

## 实验 3: MoE Output Stability 数据采集 (Fig.4)

### 设计动机

展示 decoded token 的 routed expert output（`experts.forward_impl` 的返回值，即 dispatch → fused_moe kernel → combine 之后的 tensor，**不包含 shared expert**）在相邻迭代间高度稳定（cos_sim ≈ 0.98），而 MASK token 变化显著（cos_sim ≈ 0.68-0.76）。

**关键区分**：TV6 cache 的是 routed expert output（不含 shared expert），所以动机图也应该只对比这部分。Shared expert 每步都计算，不是 cache 对象。

### 设计讨论

最终确定箱型图设计：
- X 轴：3 个数据集（GSM8K, HumanEval, MT-Bench）→ 证明现象跨数据集一致
- Y 轴：Cosine similarity（相邻 forward 的 MoE output cos_sim）
- 每组 2 个 box：Decoded (navy) vs MASK (rust)
- "Stable decoded" = 在 t-1 和 t 都是 decoded 的位置
- "Stable MASK" = 在 t-1 和 t 都是 MASK 的位置

### 实现

脚本：`codex_coding/src/collect_moe_output_stability.py`

**Hook 策略第一版（失败）**：直接 wrap `experts.forward_impl`
- 导致 `AssertionError: Forward context is not set`
- 根因：`_moe_forward_with_context` 在 line 1766-1775 try 块内设置 forward context 并调用 `experts.forward_impl`。如果 try 块抛异常（我们的 wrapper 被调用但 context 丢失），fallback 到 line 1778 无 context 路径
- 实际上是 `get_current_vllm_config()` 返回 None 或异常导致走 fallback

**Hook 策略第二版（成功）**：patch `_moe_forward_with_context` 全局函数
```python
import dinfer.model.modeling_llada2_moe as moe_module
orig_moe_fwd_ctx = moe_module._moe_forward_with_context
def hooked_moe_fwd_ctx(experts, hidden_states_flat, router_logits):
    result = orig_moe_fwd_ctx(experts, hidden_states_flat, router_logits)
    lid = experts_to_lid.get(id(experts))
    if lid is not None:
        output = result[1] if isinstance(result, tuple) else result
        collector.record_layer_output(lid, output)
    return result
moe_module._moe_forward_with_context = hooked_moe_fwd_ctx
```

**Decoded mask 问题**：第一版对 decoded mask 做了 SP 分片（`chunk = is_mask.shape[0] // tp_size`），导致 mask shape [64] 与 MoE output shape [256, 2048] 不匹配。标准 dInfer 路径（无 BSP-G）MoE 处理全量 local tokens，不做 SP 分片。修复：`self.curr_decoded_mask = ~is_mask`（不分片）。

### 命令

```bash
torchrun --nproc_per_node=8 codex_coding/src/collect_moe_output_stability.py
```

|---------|----------|-------------|-------------|--------|-----------|----------|
| GSM8K | 5,578,704 | 0.97934 | 0.08906 | 1,461,480 | 0.68322 | 0.26991 |
| HumanEval | 5,433,620 | 0.97574 | 0.09759 | 1,354,244 | 0.69880 | 0.26469 |

## 实验 5: Cache Staleness 数据采集 (Fig.5)

### 设计动机

Fig.4 展示了"相邻步 cos_sim 高"，但 TV6 的 cache 不是只用一步——cache 可能持续用多步。这个实验回答："如果在 t_decode 时 cache 了 MoE output，经过 k 步后 cache 值偏移了多少？"

### 设计讨论

**与 Fig.4 的区别**：
- Fig.4: `cos_sim(output_t, output_{t-1})` — 相邻步对比，所有 decoded 位置（包括已 decode 多步的）
- Fig.5: `cos_sim(output_{t_decode}, output_{t_decode+k})` — cache baseline vs 当前值，按 gap=k 分桶

**Fig.4 得到 0.98 而 Fig.5 gap=1 得到 0.90 的差异根因**：
- Fig.4 的 pool 被**长期 decoded 位置**主导（已 decode 10+ 步，上下文几乎不变，cos_sim 极高）
- Fig.5 gap=1 只包含**刚 decode 1 步的位置**（刚从 MASK 转变，上下文还在快速变化，cos_sim 更低）

**Baseline 选择**：用户建议把 baseline 从 t_decode 改为 t_decode+1（跳过首步不稳定期），使得数值更贴近实际 cache 精度。这只影响动机图展示，实际 TV6 机制不改。

### 实现

脚本：`codex_coding/src/collect_cache_staleness.py`

**Collector 设计**：
- `_pending[lid]` = bool mask，标记"等待下一步捕获 baseline"的位置
- Step A: 上一步标记 pending 且本步仍 decoded → 捕获 baseline
- Step B: 本步新 decode 的位置 → 标记 pending（下一步捕获）
- Step C: 已有 baseline 且仍 decoded → 计算 cos_sim(baseline, current), gap = step - t_baseline
- 同时按 gap（per-token cache age）和 step（block 内迭代位置）两种维度分桶

**幸存者偏差问题**：
- gap > 20 的数据点只来自 block 最早 decode 的 token（样本极少且非典型）
- gap=25: n=568, gap=26: n=148, gap=27: n=100 → 数据不可靠
- 解决：绘图时截断到 gap/step ≤ 20

**SEM vs std 讨论**：
- SEM = std/√n，样本量 2-2.7 万/gap → SEM 极小（~0.001），在图上不可见
- 改用 ±0.25×std 作为阴影带，展示分布变异范围

### 命令

```bash
torchrun --nproc_per_node=8 codex_coding/src/collect_cache_staleness.py
```

### 数据（Step-level, 三层 weighted pooled）

| Dataset | Step=1 | Step=5 | Step=10 | Step=15 | Step=20 |
|---------|--------|--------|---------|---------|---------|
| GSM8K | 1.000 | 0.956 | 0.900 | 0.860 | 0.790 |
| HumanEval | 1.000 | 0.948 | 0.885 | 0.852 | 0.830 |
| MT-Bench | 1.000 | 0.970 | 0.945 | 0.910 | 0.870 |

Per-gap 数据（Layer 10, GSM8K, baseline=t_decode+1）：
| gap | n | mean | std |
|-----|------|------|------|
| 1 | 9156 | 0.9344 | — |
| 5 | 9020 | 0.8446 | — |
| 10 | 8376 | 0.7455 | — |
| 15 | 6864 | 0.7259 | — |
| 20 | 4004 | 0.7390 | — |

输出：`codex_coding/results/plt/cache_staleness_data.json` (27.2 KB)

### 结论

- Cache 质量从 1.0 平滑衰减到 ~0.80（step=20）
- M=5 处 avg sim = 0.96，在 quality threshold 0.95 之上
- 三个数据集趋势一致，MT-Bench 衰减最慢

## 实验 7: TV6 Patch 模块提取

### 设计动机

bench_bsp_moe_dp2.py 有 5000+ 行，所有 TV6 逻辑嵌套在 `if __name__ == "__main__"` 的闭包中，无法 import。需要提取为独立模块用于标准化实验（throughput benchmark, quality evaluation）。

### 方案讨论

**方案 A（重写）**：从 bench 脚本提取核心逻辑，去掉 COMPONENT_TIMER 等 profiling 代码，重写为独立函数。
- 优点：代码更干净
- 缺点：容易引入细节差异

**方案 B（import 复用）**：直接 import bench 脚本的模块级函数（定义在 `if __name__` 之外的），TV6 特有逻辑完整复制。
- 优点：与 bench 脚本完全一致
- 缺点：依赖 bench 脚本不被修改

最终选择 **方案 B**（经历了从 A 到 B 的切换过程）。

### 实现——三次失败与修复

**第一版（方案 A，失败 -7ms）**：
- 自定义 `SPHiddenState` 和 `AttnSPResult` dataclass
- 自定义 `_PatchEBController`（MSkipEBController 子类，只加 note_block_start）
- 自己重写 `_make_attention_rs_forward` 和 `_make_decoder_forward`（去掉 COMPONENT_TIMER）
- 结果：65.07 ms/fwd（vs bench 57.96 ms/fwd），差 7ms

**排查过程**：
1. 检查 SP-LM Head 是否生效 → `_BSPGSPHiddenState` isinstance 检查确认通过 ✅
2. 检查 OPT-2 env var → 确认 dInfer 源码处理 ✅
3. 检查 MoE cache → 逻辑完整 ✅
4. 怀疑环境退化 → 跑 bench 脚本确认 TV6 = 57.96 ms/fwd，环境正常 ✅
5. **root cause**：`_PatchEBController` 缺少 `predict_path` 方法 → bench 脚本的 `make_bsp_g_attn_rs_decoder_forward` 内部调用 `_record_shape(ctrl.predict_path(layer_id))` → `AttributeError` 被 dInfer 的 try-except 吞掉 → 走 fallback 路径

**第二版（方案 B，成功）**：
```python
from bench_bsp_moe_dp2 import (
    make_bsp_g_attn_rs_decoder_forward,
    make_attention_reduce_scatter_forward,
    BSPMSkipController,
    _set_experts_sequence_parallel,
    COMPONENT_TIMER,
)
```
- 直接 import bench 脚本的模块级函数
- EB controller 用 `BSPMSkipController`（含 predict_path, note_block_start 等完整方法）
- COMPONENT_TIMER.enabled = False（默认关闭，timing 代码走空路径）
- 结果：**58.36 ms/fwd**（vs bench 57.96 ms/fwd，差 0.4ms，正常波动）✅

### 最终 API

```python
from tv6_patch import apply_tv6
info = apply_tv6(model, decoder, vllm_cfg)
# model 和 decoder 被 monkey-patch，之后正常创建 BlockDiffusionLLM 即可
```

**apply_tv6 做的事**：
1. 创建 BSPMSkipController（EB K=4, K_target=40, q_major=1.0）
2. Patch gate.routing → fused_routing K=4
3. Set experts.is_sequence_parallel = True
4. Patch attention.forward → reduce-scatter（BSP-G）
5. Patch decoder_layer.forward → SP layout lifecycle（BSP-G）
6. Patch experts.forward_impl → TV6 compact dispatch/combine + in-place cache
7. Wrap decoder.block_init → TV6 cache reset + EB block clock
8. Wrap model.forward → decoded/MASK mask tracking + compact sizes 计算

- fwd 差距随 batch 增大缩小（17.6% → 3.7%），说明 K=4 vs K=8 在大 batch 下趋于一致

### Level 2: lm-eval 标准 benchmark（暂搁置）

**尝试过程**：
1. 安装 lm-eval (v0.4.11) + accelerate
2. 下载数据集到 `/data/full_datasets/`（gsm8k/openai_humaneval/mbpp/mmlu，HF save_to_disk 格式）
3. 复制 eval_dinfer.py → eval_tv6_quality.py，在 model load 后注入 TV6 patch
4. 修复多个兼容问题：batch_size 参数冲突、model_path/model_name 映射、save_path 默认值

**遇到的根本问题**：
- eval_dinfer.py 使用 `multiprocessing.spawn` + TP=8（所有 8 GPU 组成一个 TP group）
- TV6 设计基于 tp=4 dp=2：attention reduce-scatter 假设 tp=4，SP layout 假设 N/4 tokens/rank
- TP=8 下每 rank 只有 4 个 SP token（batch=1, block=32, 32/8=4），大部分 decoded 后 N_compute=0 → crash
- 即使增大 batch 避免 crash，K=4 vs K=8 routing 差异导致 fwd 差距（GSM8K: 227 vs 258），自动评分（regex 提取）放大了这个差异

**结论**：lm-eval 标准 benchmark 不适合直接比较 K=4 和 K=8 路径。正确的质量验证方式是在 bench 框架下做公平 A/B 对比（相同 prompt source + 肉眼检查）。

## 已排除的方向

| 方向 | 结果 | 原因 |
|------|------|------|
| 自定义 _PatchEBController | -7ms | 缺少 predict_path 导致 _record_shape fallback |
| 直接 wrap experts.forward_impl | AssertionError | 破坏 vllm forward context 机制 |
| 自定义 SPHiddenState | SP-LM 不影响 | isinstance 检查不通过（不同类），但后来发现不是 7ms 差距根因 |
| eval_dinfer.py TP=8 + TV6 | crash/不兼容 | TV6 需 tp=4 dp=2，TP=8 下 SP tokens 太少 |
| lm-eval strict-match on dLLM | 全 0 | dLLM 不输出 `#### 数字` 格式 |
| lm-eval flex-extract 差异 | 误导性 | regex 提取中间数字，非真实质量差异 |
| batch≤4 TV6 eval | crash | SP-LM Head local_bs=0 边界条件 |
| decoded mask SP 分片 | shape mismatch | 标准 dInfer 路径 MoE 处理全量 local tokens |
