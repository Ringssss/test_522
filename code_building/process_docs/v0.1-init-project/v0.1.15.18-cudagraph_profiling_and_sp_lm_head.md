# v0.1.15.18 CUDA Graph 探索 + 完整 Profiling + SP LM Head 优化

## 主题

CUDA Graph 可行性全面验证 + GS Path 完整组件级 profiling + 基于数据驱动的优化实施

## 动机

上轮 (v0.1.15.17) 完成了 dispatch/combine 分解（21.7ms = NCCL 7.8 + straggler 4.5 + framework 8.7），本轮目标是验证 CUDA Graph 能否消除 framework 开销，并找到真正的下一个优化杠杆。

## 实验记录

### 实验 1：MoE-only CUDA Graph

**方法**：capture 单层 FusedMoE forward_impl (dispatch+kernel+combine)

**数据**：Eager 2.43 ms/layer, Graph 2.24 ms/layer, 19层总省 0.93 ms

**结论**：MoE forward_impl 的 Python 调度开销仅 ~0.05 ms/layer，8.7ms 的 framework 开销分布在整个 forward 链路上

### 实验 2：Full Forward CUDA Graph (use_cache=False)

**数据** (batch=64, seq=64)：Eager 59.5 ms, Graph 41.5 ms → **30% 加速**

**结论**：技术可行，但 batch=512 时 OOM（中间激活 67 GB + graph 额外 19 GB > 80 GB HBM）

### 实验 3：CUDA Graph 与 KV Cache 兼容性分析

**发现**：
- KV cache 的 extend_cache (F.pad) 每个 block 重新分配 tensor → 地址变化 → graph 不兼容
- flash_attn 不支持 padding mask → 预分配 KV cache 后必须用 SDPA → 引入 30ms 退化
- 方案（预分配 + SDPA + attention mask）的退化 > graph 收益

### 实验 4：CUDA Graph at batch=512 (EB + KV cache + SDPA)

**数据**：Eager 106 ms, Graph 104 ms → 仅省 2 ms (1.9%)

**根因**：batch=512 时 GPU compute 大，kernel 间的 Python dispatch 被 GPU pipeline 完全隐藏

### 实验 5：torch.compile

**结果**：inductor backend 报错 `aten._local_scalar_dense.default`（EP dispatch 的 .cpu() sync 不被支持），warmup 挂起

### 实验 6：完整 GS Path Component Timing

**命令**：`torchrun --nproc_per_node=8 bench_bsp_moe_dp2.py --config-set bspg_source --profile-target bsp --batch-size 512 --gen-length 256 --num-runs 1 --no-quality --component-timing`

### 实验 7：nsys 深度分析

**数据**：
- GPU utilization: 71% (29% idle from kernel launch gaps)
- Single stream, zero NCCL-compute overlap
- Cross-rank compute CV < 1% (perfectly balanced)
- Cross-rank NCCL variance: 16% (2.8ms, topology-related)
- Large gaps (>50us): 16 ms/fwd total, distributed as: before NCCL 6.8ms, after GEMM 5.2ms, after NCCL 3.9ms

### 实验 8：OPT-2 (skip logits.float)

**数据**：G path 70.2 → 65.9 ms/fwd, **-4.3 ms (6.1%)**

### 实验 9：OPT-4 (fp8 dispatch)

**数据**：G path 65.9 → 67.4 ms/fwd, **+1.5 ms 退化**

**原因**：NVLink 带宽充足(250 GB/s)，fp8 cast kernel 开销 > 通信量减半的节省

### 实验 10：OPT-5 (shared expert ∥ dispatch overlap)

**数据**：~0 ms 改善（在噪声范围内）

**原因**：GPU pipeline 已经隐藏 shared expert 的延迟

### 实验 11：SP LM Head (clean version)

**数据**：G path 65.9 → 58.2 ms/fwd, **-7.7 ms (11.7%)**

**实现**：跳过最后层 TP all-gather + SP layout 上算 lm_head + 本地 decode + all-gather decoded tokens (128KB)

## 新增 Insights

### I30 (替代之前定义)

CUDA Graph 在 batch=512 下仅省 2ms (2%)，因 GPU pipeline 隐藏 Python dispatch 开销。batch=64 时可省 30%。收益与 batch 反比：batch 越大 kernel 越长，Python gap 被越好隐藏。

### I31

GS path GPU 利用率仅 71%，29% 空闲来自 kernel launch gap (16 ms/fwd >50us gaps)。所有操作在单一 CUDA stream 上串行执行，NCCL 与 compute 零 overlap。

### I32

LM head ([16384,2048]×[2048,157184]) + logits.float() = 11.5 ms/fwd (15%)，是非 MoE 最大开销项。SP LM Head 优化（在 SP layout 上计算 lm_head + 本地 decode）可省 7.7 ms (11.7%)。

### I33

fp8 dispatch 在 NVLink 环境下无效（cast 开销 > 通信节省），shared expert overlap 无效（GPU pipeline 已隐藏）。这两项说明：在 batch=512 + NVLink 高带宽配置下，通信压缩和计算-通信重叠的收益空间极其有限。
