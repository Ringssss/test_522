# v0.1.11-BD + IterSmooth 结合方案实现与测试

## Goal

在已确定的最快路径 BlockDiffusionLLMAttnmask（BD-attnmask, 75-77 tok/s）基础上，引入 IterSmooth 的 soft embedding 机制，只对当前 block 内的 mask 位置做 soft embedding，保留 BD 的截断视野和无 cache 全重算策略，验证能否减少 forward 次数从而提升吞吐。

## Changes Made

### 新增类

1. **IterSmoothBlockDiffusionIteration**（`generate_uniform.py`）：
   - 替代 BlockDiffusionIteration，在 forward 中用 `inputs_embeds` 代替 `input_ids`
   - 只对当前 block 内的 mask 位置做 soft embedding（`prob @ W_e` 加权混合）
   - prompt + 已完成 block 保持 discrete embedding
   - 支持 no-cache 和 cache 两种路径
   - 引入 threshold_decay（动态阈值）和 cont_weight（混合权重）

2. **IterSmoothBlockDiffusionLLMAttnmask**（`generate_uniform.py`）：
   - BD-attnmask + IterSmooth 结合，no-cache 路径
   - 每个 block 完成后刷回 discrete embedding
   - 保留 BD 的 block-causal attention mask

3. **IterSmoothBlockDiffusionLLMCache**（`generate_uniform.py`）：
   - BD + IterSmooth + KV prefix cache 路径
   - 用 prefill 缓存 prompt KV，decode 时只发送当前 block 的 inputs_embeds

## Key Conclusions

1. **短 prompt 上 BD+IterSmooth 成功超越 baseline**：high_w 配置 87.3-87.8 tok/s，forward 从 48 降到 42，证明 soft embedding 在 BD 截断视野下确实能加速收敛
2. **长 prompt 上 IterSmooth 反而增加 forward 次数**：51-58 vs 48，soft embedding 在长上下文中增加了收敛难度
3. **KV cache 在 BD 路径上是确定的负优化**：fwd/s 从 ~26-27 降到 ~19-21，cache 管理开销（extend/pad/update/slice_scatter）远大于计算节省
4. **threshold_decay 是必要的**：无 decay 时 iter_threshold 恒为 1.0，forward 暴增到 116-121
5. **fwd/s 恒定 ~26-27（no-cache）**：h2e 的额外开销（O(block_len × V × d)）可以忽略不计
6. **性能差异 100% 来自 forward 次数**：这一结论再次被确认

## Analysis: 短/长 prompt 差异原因

- 短 prompt (6 blocks, 192 total tokens)：上下文短，soft embedding 帮助模型更快建立置信度，forward 减少 6 步
- 长 prompt (25 blocks, 800 total tokens)：上下文长，模型条件更强，soft embedding 引入轻微噪声反而干扰收敛
- iter_no 在所有 block 间累积，threshold_decay 只影响前 5 步（max(1-0.02×5, 0.90)=0.90），之后阈值一致
- 长 prompt 的第一个 generation block 浪费 ~5 步高阈值 forward，后续 block 因 soft embedding 噪声额外增加 forward

## Deep Analysis: dInfer Attention Architecture and Decoder Computation

### Attention is NOT Paged Attention

dInfer's attention implementation is **transformers-library level**, not vllm-style paged attention:

- `modeling_llada2_moe.py` provides three attention classes:
  - `LLaDA2MoeAttention` (eager): raw PyTorch `Q @ K^T → softmax → @ V`
  - `LLaDA2MoeFlashAttention2`: calls flash_attn Python wrapper
  - `LLaDA2MoeSdpaAttention`: calls `torch.nn.functional.scaled_dot_product_attention`
- All three are standard transformers attention, not vllm's PagedAttention kernel

- KV Cache management (`utils.py:KVCache`):
  - Data: one contiguous tensor `[num_layers, 2, batch, heads, seq_len, head_dim]`
  - Extend: `F.pad(past_key_values._data, pad=(...))` — naive pad
  - Update: `slice_scatter(key_states, dim=2, start=..., end=...)` — in-place copy
  - Or: `torch.cat([old_keys, new_keys], dim=2)` — prefix append
  - This is exactly transformers DynamicCache pattern

- Why dLLM hasn't adopted Paged Attention:
  - Paged Attention assumes **append-only** KV (AR models add 1 token per step)
  - dLLM needs **in-place rewrite**: same position's KV changes during diffusion iterations
  - dLLM needs **extend + replace**: enter new block → extend cache, iterate → replace current block KV
  - These semantics conflict with page-table-based management
  - This is also the deep reason why cache paths are consistently slower than no-cache (attnmask) paths

### Decoder (ThresholdParallelDecoder) Computation Flow

After lm_head produces logits [1, 32, 156928]:

1. `mask_index = (x[:, block_start:block_end] == mask_id)` — find mask positions
2. `get_transfer_index_threshold()` (with `@torch.compile(dynamic=True)`):
   a. Gumbel noise (temperature=0.0 → no-op)
   b. `x0 = argmax(logits, dim=-1)` — best token per position
   c. **Full softmax**: `p = softmax(logits.float(), dim=-1)` → [1, 32, 156928]
   d. `x0_p = gather(p, index=x0)` — confidence of argmax token
   e. `actual_threshold = max(confidence).clamp(upper=0.90)` — adaptive floor
   f. `transfer_index = (confidence >= actual_threshold)` — accept mask
3. Write back accepted tokens to x.data

### Can the Softmax be Simplified?

Yes, but savings are negligible:
- Only need `p(argmax)`, not full distribution
- Can use `exp(logits[argmax] - logsumexp(logits))` instead of full softmax
- Saves ~20MB intermediate tensor, ~0.006ms per step
- But each step is ~37ms → savings = 0.016%
- **Not worth optimizing**

### Alternative Decoding Strategies (Discussion, Not Implemented)

- **Logit margin**: `logits[1st] - logits[2nd] > threshold` — no softmax needed at all
- **Top-k based decisions**: use information from multiple top candidates
- **Block-level collective decisions**: jointly consider multiple positions
- These could potentially change forward counts (the real performance lever)
