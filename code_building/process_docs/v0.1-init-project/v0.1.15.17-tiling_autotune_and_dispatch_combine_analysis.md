# v0.1.15.17 Tiling Config Auto-Tune + Dispatch/Combine 开销分析

## 主题

FusedMoE tiling config 独立 auto-tune for E=32,N=512 + dispatch/combine 通信开销根因分析

## 动机

上轮 (v0.1.15.16) 发现 E=32/34/36 的 tiling config 完全复制自 E=256 (I27)，本轮做独立 auto-tune 验证是否有端到端收益。随后深入分析 dispatch/combine 的通信开销结构。

## 实验记录

### 实验 1：Low-M Grid Search (M=256-2048)

**命令**：`CUDA_VISIBLE_DEVICES=0 python autotune_fused_moe_e32.py --mode all`

**数据**（384 configs per M，synthetic benchmark，E_global=32 all-local）：
| M | Current E=32 | Best Found | Speedup |
|---|---|---|---|
| 256 | 0.0783 ms | 0.0598 ms | **1.31x** |
| 512 | 0.0783 ms | 0.0615 ms | **1.27x** |
| 1024 | 0.0755 ms | 0.0715 ms | **1.06x** |
| 1536 | 0.0952 ms | 0.0752 ms | **1.27x** |
| 2048 | 0.1002 ms | 0.0910 ms | **1.10x** |

**结论**：BSK=64 全面优于 E=256 的 BSK=128。但这些 M 值不是实际推理的工作点。

### 实验 2：M 值验证（Instrumentation）

**方法**：Monkey-patch `try_get_optimal_moe_config` 打印实际 M 值

**发现**：
- 实际推理中 M=16384 (decode) 和 M=32768 (prefill)
- 原因：AgRs dispatch 做 AllGather，每个 GPU 收到全量 tokens
- GS path: N_sp=2048 × 8 ranks = 16384
- A path: local_bs×block_length × dp_size = 8192 × 2 = 16384

### 实验 3：High-M Grid Search (M=8192-32768)

**数据**：
| M | Current E=32 | Best Found | Speedup |
|---|---|---|---|
| 8192 | 0.2489 ms | 0.2478 ms | 1.00x |
| 16384 | 0.4779 ms | 0.4663 ms | 1.02x |
| 32768 | 0.9643 ms | 0.9400 ms | 1.03x |

**结论**：实际 M 下 E=32 config 已近最优。差异仅 GSM 和 num_stages，2-3%。

### 实验 4：端到端 Tiling Config A/B

**命令**：标准 C12-off（torchrun --nproc_per_node=8 bench_bsp_moe_dp2.py --batch-size 512 --gen-length 256 --num-runs 2 --mode compare --config-set bspg_source --no-quality）

**数据**（GS path）：
- Baseline: 76.39 ms/fwd
- Test-B (M_eff=2048 config): 76.51 ms/fwd (+0.2%)
- Test-C (M_eff=256 小 tile config): 78.56 ms/fwd (+2.8% 退化)

**结论**：小 tile 因 block waste overhead 退化。大 tile (BSM=128, BSN=256) 是最优因为 87.5% blocks early-exit，大 tile 最小化 grid size。

### 实验 5：Pre-filter Block Waste

**方法**：在 moe_align_block_size 后 compact sorted_token_ids 移除 non-local expert blocks

**数据**：GS = 77.77 ms/fwd (+1.8% 退化 vs baseline 76.39)

**结论**：Early-exit blocks 在 H100 上几乎零成本。Pre-filter 的 zero-init + indexing 开销超过节省。

### 实验 6：Joint Stats Collection (pairs, active_experts, kernel_time)

**命令**：`--collect-joint-stats --per-layer-timing --component-timing`

**关键发现**：
- Pairs 跨 GPU 极度不均衡：平均 max/min = 3.00x（Layer 0 达 4.88x）
- 热点 GPU 跨 forward 完全稳定（确定性，由 expert placement 决定）
- Active experts 相对均匀：均值 24.6/32, CV=0.07-0.19
- **3-5x pairs 不均衡 → 仅 5-7% kernel time 差异 → 19 层累加 1.77 ms/fwd**

### 实验 7：Dampening vs Batch Size

**数据**：
| batch | Σ gap (ms/fwd) | avg dampening |
|---|---|---|
| 512 | 2.0 ms | 0.10x |
| 1024 | 3.2 ms | 0.11x |
| 2048 | 6.7 ms | 0.14x |

**结论**：dampening 从 memory-bound 到 compute-bound 仅从 0.10x 增到 0.14x，远不到线性。

### 实验 8：Component Timing 跨 Batch Size

**GS Path 数据**：
| batch | dispatch max | qa max | qa tail | combine max | combine tail | total tail |
|---|---|---|---|---|---|---|
| 512 | 8.3 | 20.1 | 1.0 | 12.7 | 0.7 | 1.7 |
| 1024 | 12.0 | 33.5 | 0.4 | 12.1 | 0.5 | 0.9 |
| 2048 | 21.6 | 71.3 | 1.0 | 20.4 | 0.8 | 1.8 |

**结论**：负载不均衡总损失 (kernel tail + combine tail) ~1-2 ms，占比随 batch 增大下降。

### 实验 9：NCCL Communication Micro-benchmark

**数据**（8 GPUs NVLink）：
- AllGather 9 MB 单次: 0.249 ms, algo BW ≈ 253 GB/s
- ReduceScatter 64 MB 单次: 0.225 ms, algo BW ≈ 261 GB/s
- 19× 循环 AG: 4.0 ms, RS: 3.8 ms
- fp8 (半 payload) 19× AG: 1.4 ms (3.2x faster)
- 实际推理: dispatch 8.0 ms, combine 12.7 ms → 差距 2x/3.6x vs micro-bench

### 实验 10：Overhead Isolation

**数据**（19 层 D→K→C 循环）：
| Group | Description | Time (ms) |
|---|---|---|
| G1 | Pure NCCL 19× pre-alloc | 7.8 |
| G2 | + torch.empty per call | 7.8 (+0.0) |
| G3 | + dummy kernel between | 8.8 (+1.0) |
| G5 | Full D→K→C cycle | 8.3 |
| G6 | Full cycle + alloc | 8.4 |
| G7 | Full cycle fp8 | 3.3 (-5.0) |

**结论**：torch.empty 零成本。Kernel gap +1 ms。fp8 通信省 60%。实际推理 21.7 ms vs micro-sim 8.4 ms → 13.3 ms gap。

### 实验 11：Combine Straggler Wait 分离

**方法**：combine 前插入 cuda.synchronize() + dist.barrier()

**数据（GS path）**：
| 组件 | 无 isolate | 有 isolate |
|---|---|---|
| quant_apply | max=20.3, tail=1.01 | max=18.9, tail=0.76 |
| pre_combine_sync | — | max=0.47 |
| pre_combine_barrier | — | max=4.55 |
| combine | max=12.7, tail=0.74 | max=8.2, tail=0.08 |

**结论**：combine 12.7 ms = straggler 等待 4.5 ms + NCCL RS ~3.8 ms + framework 开销 4.4 ms

### 实验 12：torch.compile 可行性测试

**环境**：torch 2.8.0 + vllm 0.11.0

**结果**：
- torch.compile 本身不再 crash（之前 vllm 0.10.2 会 InductorError）
- 但产生大量 graph breaks (fullgraph=False)
- 后续 generate 崩溃：`Forward context is not set`（vllm 0.11.0 EP 需要 forward context）

## 新增 Insights

### I28（建议加入 ledger）

E=32 FusedMoE tiling config 在实际推理 M=16384 下已近最优（grid search 384 configs 仅 2-3% micro-bench improvement），端到端无可测改善。原因：AgRs AllGather 使 M 膨胀到 16384（8x local tokens），config 选择对应的大 M 已是 E=256 的最优区间。

### I29（建议加入 ledger）

AgRs dispatch+combine 21.7 ms/fwd 的完整分解：NCCL 通信 7.8 ms (36%) + straggler 等待 4.5 ms (21%) + framework/Python 开销 8.7 ms (42%)。最大瓶颈是 framework 开销，EPLB 只能优化 straggler 的 kernel 成分（~2 ms），fp8 通信压缩可省 ~5 ms (NCCL 部分)，CUDA Graph 可省 ~8.7 ms (framework 部分)。

### I30（建议加入 ledger）

torch.compile(mode='reduce-overhead') 在 vllm 0.11.0 下不再 crash，但有大量 graph breaks 且与 EP forward context 不兼容。EB 的时间局部性（77.8% hot_skip 路径 s_mask 不变）为手动 CUDA Graph 提供天然分阶段策略：hot_skip → graph replay, cold/hot_update → eager。

## 已排除的优化方向更新

| 方向 | 结果 | 原因 |
|---|---|---|
| EPLB 负载均衡 | ~2 ms (2.6%) | kernel 分布无关 + dampening 0.10x |
| Tiling config auto-tune | 无效 | 实际 M=16384 已最优 |
| Pre-filter block waste | -1.8% 退化 | Early-exit 零成本 |
| 小 tile config (M_eff) | -2.8% 退化 | Block waste > tiling 收益 |
| DeepEP AlltoAll | +66% 退化 | NVLink AllGather 更优 |

## 当前最优配置

- GS path: 76.4 ms/fwd (batch=512, no timing overhead)
- tp=4, dp=2, ep=8, SP enabled
- flash_attn + fused_routing + fused_rmsnorm + EB (K=4)
- EPLB OFF

## 下一步方向（讨论中）

1. **CUDA Graph**：torch.compile 初步可行但需解决 forward context 兼容 + graph breaks
   - EB temporal locality (77.8% hot_skip) 可做分阶段 graph capture
   - 预期收益：~8.7 ms framework overhead 消除 → ~11%
2. **fp8 通信压缩**：dispatch+combine NCCL 部分可省 ~5 ms (6.7%)
3. **手动 CUDA Graph POC**：不依赖 torch.compile，手动 capture decode forward
