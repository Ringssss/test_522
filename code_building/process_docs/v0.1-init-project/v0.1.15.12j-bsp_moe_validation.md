# v0.1.15.12j — BSP-MoE Monkey-Patch Validation

## Goal

验证 Block Sequence Parallel MoE（BSP-MoE）在 C12 标准配置下是否能消除 TP group 内 MoE token 维度冗余，并判断它是否值得从 monkey-patch 继续推进到更原生的实现。

本轮目标不是混入 Scheme3、topk compaction、expert pruning 或 scheduler 改动，而是单独验证 BSP-MoE 机制：

1. 在 MoE block 入口把 `[bsz, seq_len, hidden]` flatten 成 `[N, hidden]`。
2. 用 vLLM `sequence_parallel_chunk` 在 TP group 内切分 token。
3. 只在 TP-local token shard 上执行 shared expert、gate logits 和 native `FusedMoE.forward_impl`。
4. 临时设置 `experts.is_sequence_parallel=True` 和 `experts.sp_size=tp_size`。
5. 用 `tensor_model_parallel_all_gather(..., dim=0)` 收集 TP-local 输出并裁剪 padding。
6. 保持 EB/S_mask routing 留在 native FusedMoE 内部，避免在 TP-local logits 上改变语义。

## Implementation

新增独立脚本：

- `codex_coding/src/bench_bsp_moe_dp2.py`

未修改 dInfer / vLLM 源码。BSP 只通过 monkey-patch `LLaDA2MoeSparseMoeBlock.forward` 做机制验证。

关键约束：

| Constraint | Handling |
|---|---|
| EB/S_mask 必须保持全局语义 | routing 仍由 native `FusedMoE.forward_impl` 在 EP dispatch 后执行，cold/hot_update 看到 global gathered logits |
| collective call order 不能错 | baseline 和 BSP 都保持每层每 forward 固定进入 native FusedMoE collective 路径 |
| 先形状验证再谈性能 | 先跑 smoke 和 C12 shape probe，再跑 e2e/component timing |
| 不混合 Scheme3 | 不做 routing-logits compact payload，不做预计算 topk，不做 expert pruning |

脚本内保留 `sys.modules["deep_ep"] = None` guard。当前环境下如果让 runtime 导入 broken DeepEP，会遇到 NCCL symbol 问题；已有多卡实验也采用同一 guard。

## Shape Validation

Shape probe result:

- Log: `codex_coding/results/bsp_moe_shape_probe_c12_8g_20260427.log`
- JSON: `codex_coding/results/bsp_moe_shape_probe.json`

C12 shape probe confirmed the original earlier `batch/tp` intuition needed to account for `block_length=32`: the effective MoE token count is `N=local_bsz * seq_len`, not just `local_bsz`。

| Path | bsz | seq_len | Baseline N_dp | BSP tp | BSP N_sp | Padding |
|---|---:|---:|---:|---:|---:|---:|
| prefill_fallback | 256 | 96 | 24576 | 4 | 6144 | 0 |
| cold | 256 | 64 | 16384 | 4 | 4096 | 0 |
| cold/hot block | 256 | 32 | 8192 | 4 | 2048 | 0 |

结论：BSP 在 C12 下不是把 256 个 request 切成 64 个 token，而是把 block 内 `256 * 32 = 8192` 个 MoE tokens 切成每 TP rank `2048` 个 tokens。这仍然是足够大的 MoE token shard。

## Component Timing

Component timing run 只用于 breakdown，不作为端到端速度结论，因为 CUDA event timing 和 monkey-patch wrapper 会引入额外开销。

- Log: `codex_coding/results/bsp_moe_c12_8g_component_timing_20260427.log`
- Summary: `codex_coding/results/bsp_moe_c12_8g_component_summary_20260427.json`

| Config | End-to-end | Fwd | ms/fwd | vs A |
|---|---:|---:|---:|---:|
| A) C12-AgRs baseline | 20.880s | 266 | 78.50 | — |
| B) C12-BSP-MoE | 22.237s | 266 | 83.60 | +6.50% |

Rank-max component timing:

| Component | A ms/fwd | B ms/fwd | Delta |
|---|---:|---:|---:|
| moe.bsp_chunk | n/a | 0.858 | +0.858 |
| moe.shared | 2.042 | 3.376 | +1.334 |
| moe.gate_logits | 4.916 | 2.705 | -2.211 |
| moe.native_forward | 40.343 | 37.796 | -2.547 |
| moe.dispatch | 5.756 | 7.822 | +2.066 |
| moe.quant_apply | 20.510 | 20.105 | -0.405 |
| moe.combine | 3.587 | 8.284 | +4.697 |
| moe.tp_all_reduce | 4.718 | n/a | -4.718 |
| moe.tp_all_gather | n/a | 2.618 | +2.618 |

Communication payload:

| Payload | A MB/fwd | B MB/fwd | Delta |
|---|---:|---:|---:|
| dispatch_payload | 826.877 | 206.719 | -75.0% |
| tp_gather_payload | n/a | 165.375 | +165.375 MB/fwd |

解释：

- BSP 确实把 MoE dispatch payload 从 `826.877 MB/fwd` 降到 `206.719 MB/fwd`，机制成立。
- 但当前实现新增了 TP all-gather payload `165.375 MB/fwd`。
- 更关键的是 AgRs combine 从 `3.587` 增加到 `8.284 ms/fwd`，TP all-gather 也新增 `2.618 ms/fwd`。
- 因此 component timing 说明：理论工作量减少已经出现，但当前 collective layout / monkey-patch 实现把大部分收益吃掉了。

## Interpretation

BSP-MoE 的机制结论成立：

- C12 下 MoE token 数实际为 `local_bsz * block_length`，BSP 有足够 token granularity。
- TP-local token shard 形状正确，padding 为 0。
- EB/S_mask 路径计数一致，说明 block clock 与 cold/hot/skip 语义未被破坏。
- Dispatch payload 降低 75%，说明 TP 内 MoE token 冗余确实被去掉了。

但当前 monkey-patch 还不能证明强 wall-clock win：

- 无 timing e2e 只有 `-1.40%` 小幅收益。
- component timing 显示 combine 和 TP all-gather 开销明显，timed run 反而 `+6.50%`。
- 当前瓶颈不再是“有没有理论减少”，而是 collective layout 和实现开销能不能让减少兑现。

## Conclusion

BSP-MoE 是比 Scheme3 standalone 更像系统优化的方向，因为它触及 TP group 内 shared/gate/native MoE 的 token 冗余，而不是只减少 routing logits payload。

但当前 Python monkey-patch 版本只能作为机制验证：

- 可以保留为 BSP baseline script。
- 不应直接把 `-1.40%` 当成 BSP 最终收益上限。
- 下一步如果继续，应转向更原生的 SP/MoE integration，目标是压低 AgRs combine 和 TP gather 开销，而不是继续在 Python 层堆 patch。

## Next Steps

建议下一步只选一条推进：

1. Native BSP path：把 BSP 分支内化到 LLaDA2 MoE forward 或 vLLM MoE/SP 边界，减少 Python wrapper、重复 context、额外 gather/combine。
2. Collective layout profiling：用 nsys 查看 AgRs combine 增大的真实 NCCL kernel 序列，判断是否是 SP metadata/local sizes 或 group layout 导致。
3. BSP + Scheme3 不应马上耦合；先把 BSP collective overhead 降下来，否则 Scheme3 的小收益会继续被淹没。
