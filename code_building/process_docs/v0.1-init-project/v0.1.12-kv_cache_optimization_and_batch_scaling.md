# v0.1.12 — KV Cache 优化实验与 Batch Scaling 分析

## Goal

在 BD-attnmask baseline（75-77 tok/s, batch=1）基础上，探索 KV cache 路径的性能优化，并测试多 batch 下的吞吐量扩展特性。

## Changes Made

### KV Cache 优化（两层）

**1. Lazy cache update（generate_uniform.py ~line 370, 428）**
- `BlockDiffusionIteration` 新增 `lazy_cache_update` 参数
- 当 `lazy_cache_update=True` 时，跳过块内每步的 `kv_cache.update(output.past_key_values)`
- 通过代码追踪确认：Runner 的 `past_key_values` 在循环前获取一次，manager 的 update 创建的新 KVCache 对象从未被后续迭代读取，是纯粹的无用开销
- 块间切换由 `need_cross_block_update` 机制独立处理，不依赖每步 update
- 额外修复了 cross-block update 中的 consolidate bug（`output.past_key_values._data` 为 list 时需先 consolidate）

**2. In-place write（utils.py ~line 367-380）**
- `KVCache` 新增 `use_inplace_update` 属性
- 当 `use_inplace_update=True` 时，`update()` 方法用 in-place assignment + view 替代 `slice_scatter`
- 原理：`slice_scatter` 每次分配新 800-token tensor + 全量拷贝；in-place 只拷贝 32 tokens（block 部分），返回 view 零拷贝
- `BlockDiffusionIteration` 新增 `inplace_cache_update` 参数，在 forward 中设置 `past_key_values.use_inplace_update = True`

**3. BlockDiffusionLLM 透传参数**
- `__init__` 新增 `lazy_cache_update=False, inplace_cache_update=False`
- 传递给 `BlockDiffusionIteration`

### Batch>1 支持

**4. BlockDiffusionLLMAttnmask batch>1（generate_uniform.py ~line 935-969）**
- 删除 `assert prompt.shape[0] == 1`
- `bd_attn_mask` 和 `pos_ids` 改用 `.expand(batch_size, -1, -1)` 支持多 batch
- `if decode_compl:` 改为 `if decode_compl.all():`

**5. IterSmoothBlockDiffusionLLMAttnmask batch>1（~line 1072-1107）**
- 同样删除 assert，expand tensors，修复 decode_compl check

**6. IterSmoothBlockDiffusionLLMCache batch>1（~line 1147-1206）**
- 删除 assert，修复 decode_compl check（已有 repeat 逻辑）

## Result

### Lazy cache + Inplace write（batch=1）

验证：forward 次数和生成文本与 existing cache **完全一致**（PASS）。

| 路径 | 短 prompt fwd/s | 长 prompt fwd/s |
|------|----------------|----------------|
| BD-attnmask (baseline) | 27.4 | 26.6 |
| BD+cache existing | 26.8 | 20.0 |
| BD+cache lazy | 26.9 | 20.2 |
| BD+cache inplace | 27.3 | 20.4 |
| BD+cache lazy+inplace | 27.3 | 20.4 |

- 短 prompt: inplace 几乎追平 baseline（27.3 vs 27.4）
- 长 prompt: 仍差 23%，瓶颈不在 slice_scatter 而在 GPU 利用率不足（32 tokens 喂不饱 H100）

### 4 路径 Batch Scaling（核心结论）

**短 prompt (55 tok) 总吞吐 tok/s：**

| batch | A: no-cache | B: IS no-cache | C: cache-opt | D: IS+cache |
|-------|------------|---------------|-------------|------------|
| 1 | 77 | **87** | 72 | 76 |
| 4 | 284 | **369** | 275 | 315 |
| 8 | 532 | **622** | 588 | 616 |
| 16 | 1017 | 1211 | **1225** | 1137 |
| 32 | 1634 | 1792 | **2209** | 2082 |

**长 prompt (498 tok) 总吞吐 tok/s：**

| batch | A: no-cache | B: IS no-cache | C: cache-opt | D: IS+cache |
|-------|------------|---------------|-------------|------------|
| 1 | **78** | 75 | 63 | 58 |
| 4 | **299** | 264 | 222 | 224 |
| 8 | 371 | 391 | **625** | 470 |
| 16 | 450 | 425 | **876** | 858 |
| 32 | 460 | 668 | **1672** | 1616 |

## Key Conclusions

1. **Lazy cache update 的 per-step manager.update() 不是瓶颈**——去掉后 fwd/s 无变化
2. **Inplace write 消除了 per-layer slice_scatter 开销**——短 prompt 差距从 2.2% 缩小到 0.3%
3. **长 prompt cache 路径慢 23% 的根因是 GPU 利用率不足**——batch=1 时 32 tokens 喂不饱 H100 的 132 个 SM
4. **大 batch 下存在明确的交叉点**：no-cache 路径在大 batch 时因 O(batch×seq²) 计算崩塌（长 prompt batch=32 fwd/s 降到 5.3），cache 路径 fwd/s 始终稳定 ~20-22
5. **短 prompt batch<=8: IS-nocache 最优（622 tok/s）；batch>=16: cache-opt 最优（2209 tok/s）**
6. **长 prompt batch>=8: cache-opt 大幅领先**（batch=32 时 cache-opt 1672 vs no-cache 460，**3.67x**）
7. **IS+cache (D) 始终略弱于 pure cache-opt (C)**——IS 的 soft embedding 额外计算在 cache 路径上体现更明显
8. **IS-nocache 在大 batch 长 prompt 时 forward 次数显著降低**（52→36），说明 IS 在高并行度下可能更有效
