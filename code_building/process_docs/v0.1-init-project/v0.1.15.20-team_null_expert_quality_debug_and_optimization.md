# v0.1.15.20 — TEAM Null Expert 质量排查与 MoE Cache 状态机设计

## 主题

TEAM null expert 方案的质量崩坏根因是什么？如何正确实现 decoded-token skip + cache merge？如何把 null mask 传播到所有 EP rank 而不引入额外 NCCL collective？

## 动机

上轮 (v0.1.15.19) 实现了 TEAM null expert (expert_map[256]=-1, topk_ids[decoded]=256)，kernel 独立测试通过（精确零），但完整流程质量崩坏。本轮目标：(1) 定位质量根因，(2) 设计正确的 MoE cache 状态机，(3) 解决 EP 通信问题。

## 实验记录

### 实验 1: TD1 — global_num_experts=257 单独影响

**设计动机**：隔离 V1（扩展 expert 数量到 257）对质量的影响。

**实现**：在 setup_bsp_g_attn_rs 基础上只加 `blk.experts.global_num_experts += 1`。

**命令**：
```bash
DINF_SKIP_LOGITS_FLOAT=1 DINF_SP_LM_HEAD=1 torchrun --nproc_per_node=8 bench_bsp_moe_dp2.py --config-set team_debug --profile-target bsp --batch-size 128 --gen-length 128 --num-runs 1
```

**数据**：
| Config | ms/fwd | path counts | 质量 |
|--------|--------|-------------|------|
| G | 55.22 | 19/95/2299/551, fwd=156 | ✓ 正常 |
| TD1 | 53.65 | 同 G | ✓ 正常（逐字一致） |

**结论**：V1 无害。moe_align_block_size 多一个空 bucket 不影响 MASK token 的 expert 分配。

### 实验 3: TD3 — topk_ids[decoded]=256 (routing wrap)

**设计动机**：引入 V3（将 decoded tokens 路由到 null expert），这是 null expert 机制的核心。

**实现**：TD2 + custom_routing_function wrap，在 select_experts 返回后设 `idx[decoded]=256`。decoded mask 通过 EP AllGather 获取。

**数据**：
| Config | ms/fwd | fwd | path counts | 质量 |
|--------|--------|-----|-------------|------|
| TD3 | 79.9 | 157 | 19/95/**2318**/551 | ✗ **崩坏（乱码）** |

path counts 变化（hot_skip 2299→2318, fwd +1）是质量崩坏导致的 EB 决策漂移的结果，不是原因。

**结论**：**V3 是质量崩坏的唯一根因。**

### 实验 4: TD5 — 纯 passthrough wrapper（控制实验）

**设计动机**：确认 types.MethodType 包装 forward_impl + model.forward/block_init wrapper 本身不影响质量。

**实现**：wrap forward_impl 但内部直接 return orig_impl(hs, rl)，不做任何修改。

**数据**：质量与 G 逐字一致。

**结论**：wrapper 框架无问题。之前观察到的 TD5 质量崩坏是因为在 TD4 之后跑，decoder.block_init 被 TD4 的 wrapper 污染（restore_blocks_and_experts 未恢复 block_init）。

**修复**：在 restore_blocks_and_experts 中加入 `decoder.block_init = orig_block_init` 恢复。

### 实验 7: TD7b — MASK output A/B compare（决定性实验）

**设计动机**：直接验证 null expert 是否影响 MASK token 的 MoE 输出。

**实现**：在同一个 forward 中，对相同的 hidden_states 分别调用 `fused_experts`（正常 routing vs null expert routing），对比 MASK 位置的输出。

**命令**：
```bash
DINF_SKIP_LOGITS_FLOAT=1 DINF_SP_LM_HEAD=1 torchrun --nproc_per_node=8 bench_bsp_moe_dp2.py --config-set team_debug --profile-target bsp --batch-size 512 --gen-length 256 --num-runs 1 --no-quality
```

**数据**：
```
[TD7b-DIAG] Layer 0, N=4096, n_mask=3584, n_dec=512
[TD7b-DIAG] MASK output normal norm: 9.25
[TD7b-DIAG] MASK output null   norm: 9.25
[TD7b-DIAG] MASK diff: max=0.000000, mean=0.000000
[TD7b-DIAG] Decoded output normal norm: 11.81
[TD7b-DIAG] Decoded output null   norm: 0.00
[TD7b-DIAG] MASK outputs IDENTICAL. Null expert does NOT corrupt MASK.
```

**结论**：**null expert kernel 完全正确**。MASK token 输出精确一致（diff=0），decoded token 正确输出零。方向 (a)(b)(c) 全部排除。

**质量崩坏的真实机制**：decoded=0 通过 residual connection（hidden = attn + 0）进入下一层 → attention 对所有 token 做 cross-attention → 读到缺失 MoE 的 decoded hidden states → MASK 计算被间接污染。需要 cache merge 在每层补偿 decoded 位置。

### 实验 8: Cross_block forward 发现

**设计动机**：诊断 TD4（null expert + cache merge）为什么仍然质量崩坏。

**实现**：在 model_forward 中打印每次 forward 的 input_ids shape、N_sp、step_in_block。

**数据**（batch=512, gen=256, 扩展到 40+ forwards）：
```
call=0  step=0  input_ids=[256, 96]  N_sp=6144  ← prefill
call=1  step=0  input_ids=[256, 32]  N_sp=2048  ← block 0 cold (block_init reset)
call=2  step=1  input_ids=[256, 32]  N_sp=2048  ← block 0 hot
...
call=28 step=27 input_ids=[256, 32]  N_sp=2048  ← block 0 last hot
call=29 step=0  input_ids=[256, 64]  N_sp=4096  ← block 1 CROSS_BLOCK!
call=30 step=1  input_ids=[256, 32]  N_sp=2048  ← block 1 first hot
...
```

**关键发现**：Block 1+ 的第一个 forward 是 **cross_block forward** [256, 64] (N_sp=4096)，处理 prev_block + curr_block。这是 KV cache 一致性机制。

**从源码确认**（`BlockDiffusionRunner.decode` line 275-294）：
```python
if self.need_cross_block_update:
    cross_block_x = x[:, block_loc.start-block_length:block_loc.end]  # 64 positions
    output = self.diff_iteration.forward(..., cross_block_x, ...)
    kv_cache.update(output.past_key_values._data[:, :, :, :, :block_loc.start])
```

目的：用 Block 0 的**最终 decoded tokens** 重新计算 KV cache（之前 KV cache 存的是 MASK 状态时的值）。

**影响**：cross_block forward 的 N_sp=4096 与 hot forward 的 N_sp=2048 不同，导致 MoE cache shape 不匹配。

### 实验 10: Prev_decoded 状态机 + M=5 刷新

**设计动机**：通过周期性全量计算刷新 cache，减少 cache staleness。

**实现**：
- `null_mask = decoded_sp & prev_decoded_sp & (step % M != 0)`
- M=5：每 5 步全量计算刷新 cache
- block_init 重置 step=0, prev_decoded=None, cache 清空
- prev_decoded.shape 不匹配时自动降级为 G 路径（处理 prefill/cross_block）

**数据**（C12，质量）：
| prompt | G | TD4 M=5 |
|--------|---|---------|
| #0 | "step by step" | "step by step" ✓ |
| #13 | "logic puzzle step by step" | "logic puzzle step by step" ✓ |
| #19 | "**n-th** Fibonacci number**:**" | "nth Fibonacci number:" ⚠ 极轻微 |
| #28 | "not 8 planets — there are **eight**" | "not 8 planets, but 8 planets" ⚠ 轻微 |

**结论**：M=5 刷新大幅改善质量。#0/#13 与 G 逐字一致，重复词现象消失。

### 实验 11: NCCL Deadlock 排查

**设计动机**：TD4 的独立 AllGather（同步 decoded mask across EP ranks）频繁导致 NCCL collective timeout。

**根因分析**：
1. `dist.all_gather` 要求所有 rank 发同样 shape 的 tensor。但 prefill(N_sp=6144)、cross_block(N_sp=4096)、hot(N_sp=2048) 有不同 N_sp → 如果某些 rank 不同步 → shape mismatch
2. `null_mask_sp.any()` 在不同 TP rank 上可能不一致（SP chunk 中 decoded 分布不均）→ 一些 rank 调 AllGather，另一些跳过 → collective mismatch
3. warmup → 正式 run 之间 step_in_block 未重置 → prefill 时 step>0 错误进入 TEAM 路径

**解决方案**：Piggyback dispatch — 将 decoded mask 搭载到已有的 dispatch AllGatherV 上，零额外 NCCL collective。

---

### 实验 12: Piggyback Dispatch 实现

**设计动机**：消除独立 AllGather，利用已有的 dispatch AllGatherV 传输 decoded mask。

**实现**：
1. `gate.get_logits` wrap：追加 null_mask_sp 作为 router_logits 的最后一列 → [N_sp, E+1]
2. dispatch AllGatherV 天然传输这一列 → gathered [N_total, E+1]
3. routing function：从 `gating_output[:, -1]` 提取 null_gathered → `gating_output[:, :-1]` 还原原始 logits → `idx[null_gathered] = null_id`
4. `restore_blocks_and_experts` 恢复 gate.get_logits（防止影响 G 路径）

**数据**：
| Config | Run 1 | Run 2 | 平均 | path counts |
|--------|-------|-------|------|-------------|
| G | 59.63 | 59.22 | 59.42 | 19/171/3933/931 |
| TD4 | 73.83 | 73.75 | 73.79 | 19/171/3933/931（一致） |

**质量**：与实验 10 一致（#0/#13 逐字一致）。无 NCCL deadlock。G 路径不受影响。

**结论**：Piggyback dispatch 方案正确。性能退化 24% 来自 per-layer overhead。

### 实验 13: TV3 Sparse Dispatch/Combine

**设计动机**：只通信 MASK tokens（减少 87% dispatch/combine payload）。

**实现**：
- dispatch 前提取 MASK-only compact tensor → AllGatherV compact → scatter 到 full buffer
- combine 后提取 MASK-only → ReduceScatterV compact → scatter 回 SP + cache merge

**数据**（component timing）：
| 组件 | G | TV3 | Δ | payload |
|------|---|-----|---|---------|
| dispatch | 8.54 | 10.28 | +1.74 | 206→38 MB (-81%) |
| quant_apply | 20.14 | 24.01 | +3.87 | 同 (full buffer) |
| combine | 8.98 | 10.25 | +1.27 | 同比减少 |
| dispatch_payload | 206.72 MB | **38.08 MB** | **-81%** | ✓ sparse 生效 |

**端到端 (no timing)**：
```
G:   59.04 ms
TV3: 69.74 ms (+18%)
```

**Python overhead 分析（per-layer, from cuda.synchronize profiling）**：
```
extract:     0.16 ms × 19 = 3.0 ms
disp_alloc:  0.14 ms × 19 = 2.7 ms
disp_post:   0.11 ms × 19 = 2.1 ms
comb_pre:    0.24 ms × 19 = 4.6 ms
```

**收支**：NCCL 节省 ~10.6 ms, Python overhead ~12.7 ms → 净退化 ~2 ms。

**结论**：**TV3 在 NVLink 8-GPU batch=512 下无净收益。** Python alloc/cat/index 开销 > 通信节省。TV3 还有正确性 bug（质量崩坏），暂搁置。

## 关键认知

### Null Expert Kernel 正确性

TD7b 证明：在同一 forward 中，null expert routing 不影响 MASK token 的 MoE 输出（diff=0.000000）。质量崩坏来自跨层 residual 传播，不是 kernel bug。

### Cross_block Forward 机制

BlockDiffusionLLM (KV cache 路径) 在 Block 1+ 首个 forward 处理 [prev_block, curr_block] (N_sp=2×hot_N_sp) 以刷新 KV cache。MoE cache 状态机需要处理这个 shape 变化。

### Prev_decoded 状态机

```
null_mask = decoded_sp & prev_decoded_sp & (step % M != 0)
```
- prev_decoded=None → null_mask=None → G 路径
- prev_decoded.shape != current → null_mask=None → G 路径
- step%M==0 → 全量计算刷新 cache
- M=5 将 cache staleness 从 ~27 步降到最多 4 步

### Piggyback Dispatch

decoded mask 搭载 router_logits 额外列通过已有 dispatch AllGatherV 传输。零额外 NCCL。解决了独立 AllGather 的 deadlock 问题。

### Performance Overhead 归因

| 开销源 | ms/fwd | 来源 |
|--------|--------|------|
| td4_cache_merge | 2.63 | boolean indexing y[dec]=cache[dec] |
| td4_cache_write | 0.69 | y.detach().clone() per layer |
| piggyback cat | ~10 | torch.cat([logits, mask_col]) per layer per fwd |
| **总 overhead** | **~14** | |

## 下一步方向

1. 消除 per-layer cache clone（预分配 buffer / in-place / 只缓存 decoded 子集）
2. 消除 piggyback torch.cat（预分配 [N_sp, E+1] buffer + in-place write）
3. 或重新评估 cache-only 方案（不用 null expert，SP-local 操作，零通信，但不省 kernel）
