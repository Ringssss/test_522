# v0.1.15.12g — Scheme3 8-GPU Timing and Quality Check

## Goal

在真实 C12 标准配置下复验 Scheme3：

- GPU: 8 x H100, `CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7`
- Parallelism: `dp=2,tp=4,ep=8`
- Workload: `batch_size=512`, `gen_length=256`, `block_length=32`
- Backend: `VLLM_ALL2ALL_BACKEND=allgather_reducescatter`
- Compare:
  - `A) C12-AgRs baseline`
  - `B) C12-Scheme3 (route-before-dispatch)`
  - `B2) C12-Scheme3-native-topk`

目标是确认：

1. Scheme3 期望的 dispatch payload 节省是否真实发生。
2. 该节省是否能转化为端到端收益。
3. A/B/B2 输出质量是否出现 Scheme3 特有退化。

Manual check based on the visible `Verifiable Quality` log snippets. The script prints the first 800 characters for each verifiable output, so long answers are partially truncated in the log.

| Prompt | A/B/B2 manual observation |
|---|---|
| #0 average speed | Visible derivation is correct: total distance 480 km, leg times 3h and 4h. In some snippets the final average-speed line is truncated, but no contradiction is visible. |
| #8 quadratic | Correct direction: factors are `-2` and `-3`, roots should be `2` and `3`. Output is verbose and repetitive, but semantically acceptable. |
| #13 logic | Correctly concludes B and C are true via modus ponens. There is a wording typo (`B is true B`), and later D discussion is truncated. |
| #19 Fibonacci | Iterative function is acceptable. The visible list starts correctly; snippet truncates after early values. |
| #28 planets | Planet order and visible types are mostly correct. The visible Uranus orbital period is wrong in the latest e2e log (`54.0` years; expected about `84` years), and the Neptune line is truncated. This issue is present in A/B/B2, so it is not Scheme3-specific. |

Conclusion on quality: no Scheme3-specific output degradation was observed. The remaining quality issues are shared model-generation issues rather than A/B/B2 divergence.

## Interpretation

Scheme3's theoretical communication-byte saving is real:

- A dispatch payload: `826.877 MB/fwd`
- B dispatch payload: `705.753 MB/fwd`
- B2 dispatch payload: `706.721 MB/fwd`

But the wall-clock dispatch improvement is small:

- A to B dispatch time: `5.698 -> 5.250 ms/fwd`, only `0.448 ms/fwd` saved.
- A to B2 dispatch time: `5.698 -> 5.175 ms/fwd`, only `0.523 ms/fwd` saved.

The saved bytes are dominated by:

- hidden-state payload still being the major dispatch payload;
- fixed collective overhead in AgRs allgather/reduce-scatter;
- extra control/routing overhead in the monkey-patch path;
- B2-specific pack/select/unpack and native path overhead.

Therefore, under C12-AgRs, the current Scheme3 monkey-patch implementations are negative:

- B is `+5.3%` slower than A end-to-end.
- B2 is `+7.6%` slower than A end-to-end.

## Result

Do not continue expanding the current B/B2 implementations as the main optimization path. The experiment confirms that Scheme3's routing-logits byte saving exists, but on this backend and workload it is too small in wall time to overcome added overhead.

More promising next directions:

1. If continuing Scheme3, move the decision/routing work closer to the native MoE boundary and eliminate Python-layer per-layer overhead.
2. Use `nsys` only if we need NCCL-level confirmation; current component timing already answers the main performance question.
3. Re-prioritize Sequence Parallelism, because TP-side redundant gate/routing/shared computation remains a larger opportunity than routing-logits dispatch reduction.
