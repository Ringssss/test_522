> 版本：v0.1.15.1（讨论阶段）
> 日期：2026-04-14
> 状态：讨论完成，待执行
> 前置：v0.1.14（两大方向独立 characterization 完成）

---

## 1. 目标

在保证输出质量不明显退化的前提下，探索方向一（Token Temporal Reuse）和方向二（Expert Adaptive Pruning）耦合后的**理论最小计算需求**。

当前阶段不追求 wall-clock speedup，只追求：
- 总 expert 计算节省率的上界
- 质量安全的耦合参数范围
- Pareto frontier: 计算节省 vs 质量损失

---

## 2. 两大方向回顾

### 方向一：Token Temporal Reuse（时间维度优化）
- 对于跨迭代"足够稳定"的 token，跳过整个 routed computation（gate + 全部 expert）
- 直接沿用上一步的 routed output
- 最优独立配置：
  - Config-S: margin>0.90, L4-L14, 无 drift guard (~20.8% reuse)
  - Config-D: margin>0.70, L4-L14, drift<0.02 (~22.1% reuse, ΔFwd=-4)

### 方向二：Expert Adaptive Pruning（空间维度优化）
- 每次计算时，只保留 routing weight 累积到 top-p 的 expert，低权重 expert 归零
- 最优独立配置：
  - top-p=0.80: 42.6% expert 节省, ΔFwd=0
  - top-p=0.75: 51.5% expert 节省, ΔFwd=-2（去噪效应）
  - top-p=0.70: 58.8% expert 节省, ΔFwd=+1

---

## 3. 耦合架构：底座 + 叠加

### 3.1 核心设计

方向二作为**底座**（always-on），方向一作为**叠加层**：

```
对每个 (step t, layer l, token i):
  if token_i passes Config-S/D check AND layer l ∈ safe_range:
    → 完全跳过：不算 gate，不算任何 expert，沿用上一步 routed output
  else:
    → 必须算：但只算 top-p 需要的 ~4 个 expert，不算全部 8 个
```

### 3.2 为什么方向二是底座

- 方向二覆盖所有位置、所有层、所有 token
- top-p=0.75 已验证质量中性甚至正面（ΔFwd=-2）
- 不需要跨迭代状态追踪
- 方向一是方向二的"上位替代"：凡 D1 能覆盖的位置，D2 就不需要出场

### 3.3 理论计算节省估算

- D1 覆盖 ~22% 位置（stable tokens in L4-L14）：节省 100% routed compute
- D1 未覆盖 ~78% 位置：节省 D2 的 ~51.5%
- 总节省 ≈ 22% × 100% + 78% × 51.5% ≈ **62%**
- 如果 pruned 环境下 reuse rate 上升（正面效应），可能到 **65%+**

---

## 4. 三个隐含假设

耦合架构建立在以下假设上。实验设计必须能区分哪个假设被打破。

### 假设 A：top-p pruning 是质量中性的"去噪"
- top-p 不引入新的误差源
- pruned 环境下的序列动态更平滑、更可预测

### 假设 B：方向一的 proxy 在 pruned 环境下仍然有效
- margin、drift guard 的安全阈值不需要大幅调整
- 安全层范围（L4-L14）仍然成立

### 假设 C：两者的误差独立，不相互放大
- pruning 误差和 reuse 误差的叠加是线性的，不是乘性的
- 不存在"误差共振"

## 5. 实验方案

### 第一步：在方向二底座上重新审视方向一的特性

固定 top-p=0.75 作为新 baseline，测量：

1. **token 稳定性变化**：跨迭代 margin 分布、routing overlap 等信号是否变化？reuse 候选比例是增还是减？
2. **安全层范围**：L4-L14 是否仍然安全？能否扩大（L3-L15）？
3. **drift guard 有效性**：drift<0.02 阈值是否需要调整？

### 第二步：联合参数扫描

| top-p | margin | 层范围 | drift guard | 定位 |
|-------|--------|--------|-------------|------|
| 0.80 | 0.90 | L4-14 | 无 | 保守×保守 |
| 0.80 | 0.70 | L4-14 | 0.02 | 保守×中等 |
| 0.75 | 0.90 | L4-14 | 无 | 中等×保守 |
| 0.75 | 0.70 | L4-14 | 0.02 | **中等×中等（预期甜点）** |
| 0.75 | 0.50 | L4-14 | 0.01 | 中等×激进 |
| 0.70 | 0.70 | L4-14 | 0.02 | 激进×中等 |
| 0.70 | 0.50 | L4-14 | 0.01 | 激进×激进 |

每个配置测量：
- **ΔFwd**（相对于 top-8 no-reuse baseline）
- **总 expert 计算节省率**（D1 跳过 + D2 裁剪）
- **reuse rate**（D1 覆盖的位置比例）
- **输出文本质量**（temp=0.7 文本对比）

### 第三步：画 Pareto frontier

散点图：total expert computation saved (%) vs ΔFwd
找到质量安全边界上的最优配置。

## 6. 退路决策树：如果结果不符预期

### 6.1 退路判断的关键：同时观测 ΔFwd 和 reuse rate

必须同时观测这两个指标，才能区分是哪个假设被打破。

### 6.2 决策树

```
第一步：在 top-p=0.75 底座上，测试 Config-D（margin>0.70, drift<0.02）

├── 结果正常（ΔFwd 在 baseline ±3 以内）
│   → 假设 A/B/C 暂时成立
│   → 继续联合参数扫描，画 Pareto frontier
│
├── ΔFwd 大幅恶化（>+5），但 reuse rate 正常（~22%）
│   → 假设 C 被打破：误差共振
│   → 两种误差方向相关，叠加后超线性放大
│   → 退路：
│     - 短期：退回方向二单独（top-p=0.75 已经很强）
│     - 中期：探索"cache 补偿"新架构
│       （top-p 裁掉的 expert，用近期 cache 补偿而非归零）
│       方向一从"跳过全部计算"转变为"为被裁掉的 expert 提供低成本近似"
│       两个方向的关系从"正交叠加"转为"互补协作"
│
├── reuse rate 大幅下降（<10%），ΔFwd 变化不大
│   → 假设 B 被打破：proxy 失效
│   → pruned 环境下 token 稳定性特征发生质变
│   → 退路：
│     - 在 top-p=0.75 环境下重新做完整 characterization
│       （回到 v0.1.14.1-14.8 的实验流程，但以 pruned 环境为 baseline）
│     - 重新标定 proxy 排名、安全层范围、margin 阈值
│
└── ΔFwd 大幅恶化 + reuse rate 也下降
    → 假设 A 被打破：top-p 不是无损去噪
    → top-p 已经消耗了部分误差预算，方向一可用空间被压缩
    → 退路：
      - 转为"联合误差预算分配"框架
      - 两个方向不是底座+叠加，而是共享误差预算的竞争者
      - 总误差预算 = ε, D2 消耗 ε₂, D1 只能使用 ε - ε₂
      - 实操：D2 更保守（top-p=0.80）+ D1 更保守（margin>0.95）
      - 必须做两个维度的联合搜索
```

### 6.3 各失败模式下对方向意义的认识转变

| 假设被打破 | 方向二的新认识 | 方向一的新认识 | 耦合关系的新认识 |
|-----------|--------------|--------------|----------------|
| A (top-p非无损) | top-p 有自己的误差预算，不是免费的 | 可用误差空间被压缩 | 竞争者，不是底座+叠加 |
| B (proxy失效) | 没变，仍是好底座 | proxy 是条件依赖的，不具备泛化性 | 叠加仍可行，但需要重新标定 |
| C (误差共振) | 没变，独立时安全 | 没变，独立时安全 | 两者有结构性耦合，不能简单叠加 |

### 6.4 最坏情况的保底方案

即使所有耦合尝试都失败，方向二单独（top-p=0.75）仍然是一个强有力的结果：
- 51.5% expert 计算节省
- ΔFwd=-2（比 baseline 更好）
- 不需要任何跨迭代状态追踪
- 实现简单，只需修改 routing weights

这是我们的安全网。
