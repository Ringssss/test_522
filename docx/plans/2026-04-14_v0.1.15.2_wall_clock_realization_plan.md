|------|------------|------|------|

### 1.2 当前困境

51-66% 的 expert 计算节省目前是**纸面数字**。必须搞清楚：
1. 这些节省能否转化为真实的 kernel 时间缩短？
2. 如果能，Python 层的决策/管理开销有多大？
3. 最终 wall-clock 净收益是多少？

### 1.3 本阶段目标

**精确定位 "纸面节省 → wall-clock 收益" 路径上的每一个开销源**，为后续工程实现（内联/kernel 修改/架构选择）提供定量依据。

## 2. 开销来源完整清单

一次 MoE block forward（`LLaDA2MoeSparseMoeBlock.forward`，`modeling_llada2_moe.py:639`）的计算链：

```
hidden_states
  │
  ├─→ shared_experts(hs)          [永远要算] ~0.8ms (2%)
  │
  ├─→ gate.get_logits(hs_flat)    [永远要算] ~0.3ms (1%)
  │     │
  │     └─→ topk_idx, topk_weight
  │           │
  │           ├─→ [D2] top-p 决策逻辑   [新增开销] sort + cumsum + mask + renorm
  │           │
  │           └─→ fused_experts(hs, w1, w2, weights, ids)   [要省的部分] ~13.9ms (37%)
  │                 │
  │                 └─→ [D1] cache check + reuse scatter   [新增开销] cosine sim + mask + scatter
  │
  └─→ residual add                [永远要算] ~negligible
```

### 2.1 开销源编号

| 编号 | 开销源 | 类型 | 可消除？ |
|------|--------|------|---------|
| **C1** | fused_experts kernel 对 weight=0 expert 的处理 | kernel 内部 | 取决于 kernel 实现 |
| **C2** | gate routing 计算 | 固定开销 | 不可消除 |
| **C3** | top-p 决策逻辑（sort/cumsum/argmax/scatter/renorm） | Python + 小 CUDA kernel | 可通过 fuse 消除 |
| **C4** | D1 temporal reuse 的 cache 管理和决策 | Python + 小 CUDA kernel | 可通过内联消除部分 |
| **C5** | Python hook dispatch 本身 | Python 调用开销 | 内联后完全消除 |
| **C6** | fused_experts API 限制（固定 top-k 维度） | 接口约束 | 需要改 API 或 kernel |
| **C7** | 内联后仍不可消除的开销（gate 拆分调用等） | 架构性 | 需要评估 |

## 3. 关键问题：fused_experts 对 weight=0 的处理方式

### 3.1 为什么这是门槛问题

D2（top-p pruning）的实现方式是：保留 topk_ids 的 [N, 8] 形状不变，但把低权重 expert 的 topk_weights 设为 0。

fused_experts kernel 的处理有两种可能：

**可能性 A：逻辑跳过** — kernel 仍然为每个 token-expert pair 分配 GEMM block、加载 expert weight 矩阵、执行 GEMM，只是最后乘以 weight=0 不贡献结果。

- 此时：weight loading（瓶颈）不变，kernel 时间不变
- 51.5% 的 expert 节省在 wall-clock 上为 **0**

**可能性 B：物理跳过** — kernel 内部有 branch，当 weight=0 时跳过该 GEMM block 的 launch 和 weight loading。

- 此时：weight loading 接近减半，kernel 时间显著缩短
- 51.5% 的 expert 节省可以真实兑现

### 3.2 先验判断

从 v0.1.13 的分析已知：
- MoE kernel 算术强度 ~1.5 MAC/byte，完全 memory-bound
- 瓶颈是 expert weight 的 HBM loading（每个 active expert ~2MB weight）
- vllm 的 fused_moe_kernel 使用 `moe_align_block_size` 将每个 expert 的 token 对齐到 BLOCK_SIZE_M
- padding 的 GEMM 计算"几乎免费"（mask=0 时 tl.dot 不耗时间）

**这暗示可能性 A 更可能**：kernel 按 expert 分 block，每个 expert 都加载 weight，只是 weight=0 的 token 的 GEMM 结果不贡献。但需要实验确认。

### 3.3 另一种可能：moe_align_block_size 的间接省

即使 kernel 不显式 branch，如果某个 expert 的 token 全部 weight=0，`moe_align_block_size` 可能为该 expert 分配 0 个 block。这样 kernel 的 grid size 缩小，fewer blocks → fewer weight loads → 真实省时。

**但这只在"某个 expert 完全不被任何 token 选中"时才生效。** top-p pruning 下，一个 expert 可能被某些 token 保留、被另一些 token 裁掉。只要有任何一个 token 保留了它，该 expert 的 weight 就要被加载。

需要验证：top-p pruning 后，实际有多少 expert 变成"完全不被选中"？

## 4. 实验方案

### Step 1：fused_experts kernel micro-benchmark（门槛测试）

**目的**：回答 "weight=0 是否省了真实的 kernel 时间"

**设计**：

```
Benchmark A: 正常 routing
  - topk_weights: 全部为正值（模拟 baseline top-8）
  - topk_ids: 正常 routing 结果
  - 测量: kernel_time_A

Benchmark B: 50% weight=0（模拟 top-p=0.75 逻辑省）
  - topk_weights: 8 列中 4 列设为 0
  - topk_ids: 不变（仍然 [N, 8]）
  - 测量: kernel_time_B

Benchmark C: 物理裁剪到 top-4（模拟物理省）
  - topk_weights: 只保留 4 列（renormalized）
  - topk_ids: 裁剪到 [N, 4]
  - 测量: kernel_time_C

Benchmark D: 极端 — 只保留 top-1
  - topk_weights: [N, 1]
  - topk_ids: [N, 1]
  - 测量: kernel_time_D
```

**控制变量**：
- 使用真实模型的 w1, w2 权重矩阵
- 使用真实 routing 结果（从一次 forward 中采集）
- 固定 token 数：N=32（batch=1）, N=256（batch=8）, N=1024（batch=32）
- 每个 benchmark 重复 100 次取中位数
- 使用 `torch.cuda.Event` 做精确计时

**判断标准**：
- 如果 B ≈ A：逻辑省无效 → C1 问题确认，必须走物理裁剪路线
- 如果 B < A 但 B > C：有部分效果但不完全 → 可能是 moe_align_block_size 的间接效应
- 如果 B ≈ C：逻辑省等效于物理省 → C1 不是问题
- C vs A 的比值 = 物理裁剪的理论加速上界

**附加测量**：
- 统计 Benchmark B 下实际有多少 expert 变成"完全无 token 选中"
- 统计 moe_align_block_size 在 B vs A 下的 total blocks 数量差异

### Step 2：逐组件 profiling（开销分布锁定）

**目的**：量化每个开销源占 MoE block forward 的比例

**设计**：对一次完整 forward 中的每个 MoE layer，用 `torch.cuda.Event` 插入 timing 点：

```
T0: shared_experts 开始
T1: shared_experts 结束 / gate 开始
T2: gate 结束 / top-p 决策开始
T3: top-p 决策结束 / fused_experts 开始
T4: fused_experts 结束 / D1 cache check 开始
T5: D1 cache check 结束 / residual add 开始
T6: residual add 结束
```

测量：
- T1-T0: shared_experts 时间 → C2 的一部分
- T2-T1: gate routing 时间 → C2
- T3-T2: top-p 决策逻辑时间 → C3
- T4-T3: fused_experts kernel 时间 → 这是我们要省的
- T5-T4: D1 cache 管理时间 → C4
- T6-T5: residual add 时间

**设置**：
- batch=32（与 Pareto 实验一致）
- 测量 19 层 MoE 的各组件时间
- 跑 10 次 forward 取平均

**期望获得**：
- fused_experts 占 MoE block 时间的精确比例（预期 ~90%+）
- top-p 决策逻辑的绝对开销（单位 ms）
- D1 cache 管理的绝对开销
- 19 层的逐层时间分布（是否有层间差异）

### Step 3：hook overhead isolation（Python 开销隔离）

**目的**：分离 Python hook dispatch 开销 vs 实际逻辑开销

**设计**：在同一个模型上，比较三种 forward 模式的 wall-clock：

```
Mode 0: 原始 forward（model.forward 直接调用，无任何修改）
  → 基准线

Mode 1: Transparent hook（替换 moe.forward，但内部只调用原始逻辑）
  → 与 Mode 0 的差值 = 纯 Python hook dispatch 开销 (C5)

Mode 2: Top-p only hook（替换 moe.forward，执行 top-p pruning）
  → 与 Mode 1 的差值 = top-p 逻辑本身的开销 (C3)

Mode 3: Full coupled hook（top-p + D1 temporal reuse）
  → 与 Mode 2 的差值 = D1 cache 管理开销 (C4)
```

**测量**：
- 每种模式跑一次完整 generate（gen_length=128, batch=32）
- 测 wall-clock time 和 per-forward time
- 重复 3 次取平均

**期望获得**：
- C5（hook dispatch 开销）的绝对值和占比
- C3（top-p 逻辑）的绝对值和占比
- C4（D1 cache 管理）的绝对值和占比
- 三者之和 vs v0.1.14.6-7 观测到的 15-20% 慢是否吻合

## 5. 决策分叉树

### 5.1 Step 1 结果驱动的路线选择

```
Step 1: fused_experts 对 weight=0 是否物理跳过？

├── 情况 α：物理跳过（kernel_time_B ≈ kernel_time_C，两者远小于 A）
│   │
│   │  → D2 的 expert 节省可以直接通过 weight=0 兑现
│   │  → 不需要改 kernel 或 API
│   │  → 重点转向消除 Python 层开销（C3 + C4 + C5）
│   │
│   └── 下一步：
│       a) 将 top-p 逻辑内联到 modeling_llada2_moe.py:639 的 forward 中
│       b) 消除 hook dispatch（C5 归零）
│       c) 评估内联后的 top-p 决策开销（C3）是否可接受
│       d) 如果 C3 仍然太大：将 sort+cumsum+mask fuse 为单个 Triton kernel
│
├── 情况 β：间接跳过（kernel_time_B < A 但 B > C）
│   │
│   │  → moe_align_block_size 提供了部分效果
│   │  → weight=0 没有完全跳过，但"完全无 token"的 expert 被跳过了
│   │
│   └── 下一步：
│       a) 量化间接效果的比例（B vs A 的差值）
│       b) 评估是否足够（如果 B ≈ 0.7×A，可能已经 good enough）
│       c) 如果不够：考虑物理裁剪方案（见情况 γ）
│
├── 情况 γ：不跳过（kernel_time_B ≈ A，只有 C 显著更快）
│   │
│   │  → weight=0 方案无法兑现 wall-clock 收益
│   │  → 必须走物理裁剪路线（实际改变传入 fused_experts 的 top_k）
│   │
│   └── 分叉：
│       │
│       ├── γ-1：统一 top-k 方案（最简单）
│       │   - 把 top-p pruning 转化为 fixed top-4 pruning
│       │   - 所有 token 统一只保留 top-4 expert
│       │   - topk_ids 从 [N, 8] 裁剪到 [N, 4]
│       │   - 直接调用 fused_experts(top_k=4)
│       │   - 限制：无法做 per-token adaptive（有些 token 可能需要 5 个）
│       │   - v0.1.14.9e 已验证 fixed top-4 ΔFwd=+1（可接受）
│       │
│       ├── γ-2：token grouping 方案（较复杂）
│       │   - 按 kept_k 分组：group_4 = tokens with 4 experts, group_5 = ...
│       │   - 每组分别调用 fused_experts
│       │   - 保留 adaptive 能力
│       │   - 但多次 kernel launch 可能抵消 expert 节省
│       │
│       ├── γ-3：修改 fused_moe Triton kernel（最灵活）
│       │   - 在 kernel 内部加 branch：if weight == 0 skip this block
│       │   - 改动最小：只改 Triton kernel 的内层循环
│       │   - 但需要理解 vllm kernel 的 tile/warp 调度细节
│       │   - 风险：可能破坏 autotuning 配置
│       │
│       └── γ-4：接受 kernel 不变，只兑现 forward 次数收益
│           - D2:tp75 → ΔFwd=-2 → 2/149 = 1.3% wall-clock 节省
│           - D1 alone → ΔFwd=-4 → 2.7% wall-clock 节省
│           - 总计 ~4%
│           - 这条路线放弃 MoE kernel 加速，转向论文故事为主
```

### 5.2 Step 2+3 结果驱动的内联策略

```
C5 (hook dispatch) + C3 (top-p logic) + C4 (D1 cache) 的绝对开销 = X ms/forward

├── X < fused_experts 节省量（情况 α/β 下）
│   → 净 wall-clock 正收益
│   → 内联即可
│
├── X ≈ fused_experts 节省量
│   → 需要进一步优化 C3/C4
│   → 将 top-p fuse 为 Triton kernel
│   → 将 D1 cache 改为 pre-allocated buffer（消除 dict lookup + clone）
│
└── X > fused_experts 节省量
    → 即使 kernel 能省，Python 层开销抵消了
    → 必须同时解决 kernel + Python 层
    → 或者放弃 D1，只兑现 D2（D2 的 C4=0，开销更小）
```

## 7. 与 v0.1.15.1 Pareto 配置的关系

每个 Pareto 配置的理论 wall-clock 收益由以下公式决定：

```
理论净收益 =
    (fused_experts 单层时间) × (expert 节省率) × (19 层) × (forward 次数)
  - (C3 开销/层) × (19 层) × (forward 次数)      [如果 D2 active]
  - (C4 开销/层) × (11 层) × (forward 次数)      [如果 D1 active, L4-L14]
  - (ΔFwd 额外 forward) × (full forward 时间)    [如果 ΔFwd > 0]
```

| 配置 | Expert 节省 | ΔFwd | D2 active | D1 active | 理论优势 |
|------|------------|------|-----------|-----------|---------|
| D2:tp75 | 51.5% | -2 | 是 | 否 | 最少额外开销（无 C4），且少 2 forward |
| D1+D2:tp75_m90 | 61.5% | +2 | 是 | 是 | 更多节省但有 C4 且多 2 forward |
| D1+D2:tp70_m70_d02 | 66.2% | +4 | 是 | 是 | 最多节省但有 C4 且多 4 forward |

**D2:tp75 单独可能是 wall-clock 最优配置**：
- 没有 D1 的 cache 管理开销（C4=0）
- 少 2 次 forward（省了完整 forward 时间）
- 理论 expert 节省稍低但净收益可能更高

这需要 Step 2 的数据来验证。

## 8. 与已有 profiling 数据的交叉参考

v0.1.13 的 forward 时间拆分（no-cache, batch=1, ~192 tokens）：

| 组件 | 时间 | 占比 |
|------|------|------|
| Routed MoE (fused_experts) | 13.9ms | 37% |
| Shared expert (dense FFN) | 0.8ms | 2% |
| Gate (router) | 0.3ms | 1% |
| Attention + Norm + Embedding + LM head | 22.0ms | 60% |
| **Total forward** | **~37ms** | 100% |

如果 fused_experts 能实现 51.5% 的时间缩短：
- 节省 13.9ms × 51.5% = **7.2ms/forward**
- 占 total forward 的 7.2/37 = **19.4%**

但这是 batch=1 的数据。batch=32 下 MoE 占比可能更高（因为 attention 不变但 MoE 处理的 token 数 ×32）。Step 2 会给出 batch=32 的精确数据。

## 附录 B：所需的 vllm kernel 源码位置（Step 1 前需阅读）

需要理解 fused_moe_kernel 的以下细节：
1. 它如何使用 moe_align_block_size 的输出（sorted_token_ids, expert_ids, num_tokens_post_padded）
2. 当某个 expert 的 num_tokens_post_padded = 0 时，kernel 是否跳过该 expert
3. weight=0 的 token 在 GEMM block 中是否被 mask 掉还是正常计算
